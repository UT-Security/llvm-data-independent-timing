# Decrypt-then-parse in the wild: where a KEY-class secret leaves a crypto primitive and is handled by non-crypto glue

Research memo for the third DIT case study ("the secret leaves the primitive"). All numbers carry a URL; "unverified" marks what could not be pinned to a primary source. Local measurements were done on this host with OpenSSL 3.5.3 and are labelled as such.

## 0. Ranked verdict (details in section 4)

1. **TLS session-ticket resumption on the server (OpenSSL / mbedTLS / s2n-tls).** Key-class secret (48-byte master secret or resumption PSK) leaves AES-CBC/GCM and is DER- or byte-parsed by non-crypto code before it re-enters HKDF/PRF. Event is frequent (about 40% of HTTPS connections at Cloudflare; 9-12% of TLS 1.3 connections in 2019 passive data), the glue is small (about 130-150 bytes of plaintext, about 20 fields), the knob is the resumption rate and tickets-per-handshake, and the protocol itself says which fields are secret (RFC 5077 section 4 StatePlaintext: only master_secret is key material) and where the result becomes one public bit (binder compare, ticket-age compare). No deployed library treats this parse as constant-time today; s2n-tls comes closest.
2. **Runner-up: Kerberos AS-REP / TGS-REP / ticket decrypt in MIT krb5.** Session key leaves the enctype decrypt and goes through a generic table-driven ASN.1 decoder (EncKDCRepPart, EncTicketPart) into a krb5_keyblock. Massive deployment (Active Directory in about 90% of the Global Fortune 1000), per-logon and per-service frequency, but no public measurement of event rates and no prior timing-attack literature on the decoder, so motivation is weaker and the decoder is shared with public parsing (context-sensitivity cost).
3. **Honourable mention: encrypted private-key loading (PKCS#8 PBES2 / PKCS#12 / OpenSSH bcrypt format).** Strongest attack literature (Certified Side Channels, Util::Lookup, DATA) and the cleanest boundary (nothing is ever declassified), but it happens once per process, so the secret fraction is about 0 unless an artificial batch knob is introduced, and the tainted code is dominated by bignum arithmetic (primality tests, GCD, modular inversion), which makes it look like the whole-program-crypto case study again.

Rejected: encrypted cookies / JWE (plaintext is application data: taint floods the application), Tor relay cells and IKEv2 (decrypted material is traffic or identities, not keys), WireGuard (decrypted static key is an identity, not a secret key), OpenVPN tls-crypt-v2 (key-class and clean, but the glue is a single memcpy), HTTP Basic auth (password, clean with one declassification, but web prevalence is unverified; good as a secondary nginx demo).

### 1.1 Secret-fraction estimate for candidate 1

On a resumed TLS 1.3 handshake the tainted region is: ticket AES-CBC/GCM decrypt and HMAC (crypto, already CT), the ticket-plaintext parse (about 130-150 bytes, OpenSSL ASN.1 engine or mbedTLS's hand-written ~100-line loader), the ticket-age arithmetic, the cipher/hash compatibility checks, the binder HKDF and `CRYPTO_memcmp`, and the key schedule. Public work: ClientHello parsing, extension processing, record layer, HTTP. Because a resumed handshake has no signature and (with psk_ke) no key share, the glue is a larger share of the resumed handshake than of a full one; with r = 40% and 2 tickets per full handshake, the serializer (`i2d_SSL_SESSION`) runs on 60% of connections twice and the parser on 40% once. No published CPU breakdown exists: the 1-20% target has to be established by measurement in the study.

The constant-time discussion is in Appendix E.3 and explicitly concedes that the application boundary defeats it.

## 3. Prior art on this exact shape (section C)

No prior system has evaluated the decrypt-then-parse glue of a real protocol as a *protection* workload with region sizes and cost; what exists is verification of one glue function, attacks on key parsing, and one taint system whose declassification policy is the opposite of what this case study needs.

- **ct-verif (Almeida et al., USENIX Security 2016)** verified OpenSSL 0.9.8zg's MEE-CBC decryption path (1K LoC of C, 10K of Boogie: CBC decrypt, padding removal and well-formedness check, HMAC over the unpadded message with a fixed number of compression calls, constant-time MAC compare) in 18.73 s ("mee-cbc-openssl", Table 2), and cites the two s2n pull requests (#147, #179) from the Lucky Microseconds episode. This is post-decryption glue, but for record plaintext (not key-class), and it measures verification time, not protection cost. https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf
- **Binsec/Rel (Daniel, Bardin, Rezk, S&P 2020)** replays Lucky13 on OpenSSL 1.0.1 `tls-cbc-remove-padding`: 5 violations on the insecure version, full exploration of the patched version at record length 63 in 400 s; 296 samples / 64k instructions overall. Same caveat as ct-verif. https://binsec.github.io/assets/publications/papers/2020-sp.pdf
- **CryptoMPK (Jin et al., S&P 2022)** is the closest taint system and is instructive by contrast: its "crypto-aware" taint "adds the tag of crypto key to neither plaintext nor ciphertext", i.e. it declassifies every cipher output by policy. With that policy Nginx+OpenSSL has 3.06% (2149/70126) tainted memory operations; without it 9.5% ((4439+2223)/70126); 296 of 874 crypto functions (34.3%) are protected, 212 at function granularity; 7+2 initial annotations (six pkey fields and the AES_KEY) and at most 9.53% overhead. The paper states "Apache and Nginx do not access the crypto secret. They delegate the management of crypto buffers to crypto libraries." It did not evaluate session tickets, RSA premaster handling or key parsing, and its declassify-all-plaintext rule would erase exactly the flow this case study is about (the ticket plaintext is a key). https://www.cs.wm.edu/~smherwig/readings/papers/22-oakland-crypto_mpk.pdf
- **ConTExT (Schwarz et al., NDSS 2020)**: developer annotates secrets (`nospec`), overhead 0-338% for security-critical applications in the ConTExT-light emulation; no protocol glue workload. https://www.ndss-symposium.org/wp-content/uploads/2020/02/24271.pdf
- **cio (Flanders et al., ASPLOS 2024)**: instruction-centric channels (silent stores, computation simplification) on libsodium only; overheads up to 27.84x, text size 363 kB to 1,327 kB. https://homes.cs.washington.edu/~dkohlbre/papers/cio-asplos24.pdf
- **Declassiflow (CCS 2023)** uses "declassification" in the Spectre sense (data the non-speculative execution already transmits) to remove speculative protections; workloads are CT primitives, not protocol glue (unverified in detail). https://arxiv.org/abs/2312.09336
- **Robust Constant-Time Cryptography (Kolosick et al., PACMPL 2025)** formalises that CT is a whole-program property and libraries cannot assume anything about the application; overhead <5% in most cases. https://arxiv.org/abs/2311.05831
- **Attack side, which is the real motivation for candidates 1, 3 and 4**: DATA (USENIX 2018) found key-parsing leaks in OpenSSL (`set_hex`/`isxdigit`, `hexchar2int`, `BN_bin2bn`, `ASN1_STRING_set`, `strlen`, `dsa_priv_decode` missing the CT flag) and states "analysis often neglects these information leaks because an attacker typically has no way to trigger key loading ... in practice". Certified Side Channels (USENIX 2020) and Util::Lookup (CCS 2021) turned key parsing into full key recovery (single trace in SGX for base64/PEM). All three are address-based (cache) leaks rather than the value-timing channel targeted here, but they establish that "the parse after the primitive" is a real attack surface that libraries had ignored.
- **Industry policy statements** that decrypted session state or premaster material must be handled carefully: OpenSSL `tls_process_cke_rsa` comment (quoted above) and `CRYPTO_memcmp` for ticket HMAC and PSK binders; s2n-tls `s2n_safety.h` (`s2n_constant_time_equals`, `s2n_constant_time_copy_or_dont`, `s2n_constant_time_pkcs1_unpad_or_dont`) and, tellingly, `s2n_resume.c` compares the *cipher suite bytes read out of the decrypted ticket* with `s2n_constant_time_equals`, i.e. AWS already treats decrypted ticket contents as sensitive; Go `crypto/tls/ticket.go`: "The encoding contains secret values critical to the security of future and possibly past sessions"; Go `extractPadding`: "returns, in constant time, the length of the padding"; libsodium: `sodium_base642bin` is constant-time because it "touches cryptographic inputs, such as plaintexts or keys"; Apache `mod_session_crypto` uses `ap_memeq_timingsafe` for its MAC. None of them makes the *parse* of the ticket or key constant-time, which is the gap the case study fills.

## 4. Recommendation

### Best candidate: TLS session-ticket resumption, server side ("the secret leaves the primitive")

Why it wins on all three axes:
- **Deployment reality.** Resumption is 40% of HTTPS connections at Cloudflare (2017) and about 9-12% of TLS 1.3 connections in 2019 passive traces; 77.6% of top-1M sites issue tickets; OpenSSL issues two tickets per handshake by default. The secret is a genuine 48-byte master secret / PSK, not application data. The glue is small and concrete: about 130-150 bytes of DER (measured 208-byte ticket on OpenSSL 3.5.3), ~20 fields, age arithmetic, cipher/hash checks, binder compare.
- **Knob.** Resumption rate r and tickets-per-handshake change the secret fraction from 0 to a large value while the public work (ClientHello, records, HTTP) is untouched. Client-side ticket lifetime is a second, orthogonal knob.
- **Declassification.** The protocol names the secret field (RFC 5077 section 4; RFC 8446 sections 4.6.1, 7.1) and the two one-bit exits (binder, ticket age). The rest of the ticket is public by construction, so field-level declassification is defensible and maps directly onto parameter-scoped rules. Taint tracking is genuinely needed: the secret is spread over a memcpy into a struct, arithmetic on `tick_age_add`, and comparisons, none of which a human would annotate by hand and none of which any library protects today, while s2n's constant-time cipher-suite compare shows practitioners already sense the problem.

Suggested concrete target: mbedTLS (`mbedtls_ssl_ticket_parse` -> `ssl_tls13_session_load`, hand-written, ~100 lines, no generic ASN.1 engine) with OpenSSL (`tls_decrypt_ticket` -> `d2i_SSL_SESSION` -> `tls_parse_ctos_psk`) as the harder second target that exposes the shared-decoder problem. s2n-tls is a third option whose `s2n_tls13_deserialize_session_state` is the cleanest to reason about.

Honest weaknesses:
1. The glue is microseconds against a handshake of hundreds of microseconds: the interesting result is placement precision and switch count, not end-to-end overhead, and the 1-20% secret-fraction window will have to be demonstrated by measurement (no public breakdown exists).
2. OpenSSL's ASN.1 engine is shared with public certificate parsing: without context sensitivity the pass either over-protects all DER decoding or has to clone. That is a real finding but also a risk for the numbers.
3. Whether the secret-bearing fields in the ticket (ticket_age_add, timestamps) are "public" is a policy call; the memo takes RFC 5077's StatePlaintext as the authority.
4. Ticket *issuance* (i2d + encrypt on every full handshake) touches the secret too and must be in scope or the result understates the glue.

### Runner-up: Kerberos (MIT krb5) AS-REP / TGS-REP / ticket decrypt

Strengths: unquestionably key-class (session keys), enormous deployment (about 90% of the Global Fortune 1000 run AD; Kerberos is its default protocol), events happen per logon and per service access, the RFC gives the ASN.1 for the secret field, and the KDC/service side (`krb5_decrypt_tkt_part`) is a server workload with a natural rate knob.

Weaknesses: no public measurement of AS/TGS rates or of decoder cost (secret fraction unverified); the decoder is generic and table-driven, so taint precision depends entirely on context sensitivity; there is no prior side-channel literature on Kerberos decoding to motivate the threat, and the KDC is Windows in practice (MIT krb5 is a proxy for it); the client side stores the key in a ccache (serialization glue, but rare).

### Why not the others
- Private-key loading has the best attack story and the cleanest boundary, but happens once, and its tainted code is bignum crypto (primality, GCD, inversion) rather than glue; the only way to get a secret fraction is a synthetic batch loop, which reviewers will read as whole-program crypto again.
- RSA key exchange is already constant-time inside the libraries, is a single call, and is being deprecated.
- Cookies/JWE/Tor/record padding hand the plaintext to the application: the RFC itself (8446 Appendix E.3) says constant time cannot survive that boundary.
- WireGuard and IKEv2 do not decrypt keys. OpenVPN tls-crypt-v2 does, cleanly, but the glue is a memcpy.
- HTTP Basic is a good secondary demonstration (nginx: base64 LUT decode + ':' scan + crypt + strcmp, one declassified username) but the secret is a password and web prevalence is unverified.
