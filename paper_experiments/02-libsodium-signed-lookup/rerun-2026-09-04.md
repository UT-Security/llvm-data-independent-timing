# Experiment 02 under the 2026-09-04 state: what moved

Re-run of this experiment's arms under three changes made on 2026-09-03/04:
the compiler at the `dit-tainter` tip `7a4512b21fb7` (Phase 0 seed
validation, the Phase 1 product-lattice refactor with its two under-coverage
fixes, the Phase 2 flags, sub-block placement default off), the gem5 oracle
with the store-rule fix (`gem5-DIT` #93), and the corrected libsodium seed
file `libsodium_secret.fixed.txt`. Work dir
`~/Documents/signed_lookup-gem5-rerun`; nothing under `data/` was touched.
The original arm binaries are preserved as
`gem5-DIT/benchmarks/signed_lookup/bin.orig-2026-09-04/`.

## The oracle frontier: unchanged to the last digit

The 18 oracle runs (`{base,pass,blanket} x L in {64, 1000, 20000} x iter in
{0, 4}`) were repeated with the ORIGINAL oracle binaries under the fixed
gem5, isolating the oracle change. Every number is identical:

| L | f_secret | pass uncovered | pass wasted | blanket wasted | blanket / pass |
|---|---|---|---|---|---|
| 64 | 66.54% | 5 | 1,083 | 1,805 | 1.7x |
| 1,000 | 22.54% | 5 | 1,083 | 12,335 | 11.4x |
| 20,000 | 1.56% | 5 | 1,083 | 226,085 | 208.8x |

Old oracle and fixed oracle agree on all of it, and `secret ADDRESS` is 0 in
every run. The store-rule bug needed a pointer read out of secret memory to
sustain its cycle; this flow's secret is a flat 32-byte AEAD key and the
lookups never derive an address from it, so the bug never fired here. The
40.7% denominator collapse seen on the TLS resumption flow is specific to
allocator-sized bignum work and does not touch this experiment.

One bookkeeping note: the README quotes 3,589 secret ops per request, 4
uncovered, 99.89% coverage; recomputing from the run files with the README's
own formula gives 3,590, 5, 99.87%. The difference is one operation, present
in both the old and the new runs, so it is a derivation rounding in the
README's table rather than an oracle change. The claim ("effectively sound;
the survivors are the checksum fold") stands either way.

## The seed file: the shipped one is right for this rig, and the reason is a name collision

`utils/taint_seed_check.py` found 12 dead lines in the shipped
`libsodium_secret.txt` on an UNPATCHED libsodium: a `_ref` suffix on three
ChaCha20 statics that do not carry it. This rig never builds an unpatched
libsodium. Both `build_gem5_linux.sh` and `build_native_sodium.sh` apply a
rename patch to `chacha20_ref.c` (`stream_ref -> stream_ref_ref`,
`stream_ref_xor_ic -> stream_ref_xor_ic_ref`, `chacha20_encrypt_bytes ->
chacha20_encrypt_bytes_ref`) so that the CIO-parity seed names match, and the
build log's own check shows them live: `chacha20_encrypt_bytes_ref
switches=2`, `stream_ietf_ext_ref switches=4`, `stream_ietf_ext_ref_xor_ic
switches=3`.

Why the patch exists, which the dead-seed finding missed: `stream_ref` and
`stream_ref_xor_ic` are static functions defined in FOUR translation units
of libsodium (`chacha20/ref`, `salsa20/ref`, and the two `chacha20/dolbeau`
variants). Seeds are matched by name across every TU, so an unpatched name
cannot single out the ChaCha20 reference implementation. Measured, same rig,
corrected file in place of the shipped one:

| | shipped seeds | corrected seeds |
|---|---|---|
| `chacha20_encrypt_bytes_ref` need | 297 | 116 (propagation only; its direct seed is dead) |
| `stream_ref_ref` / `stream_ref_xor_ic_ref` (chacha) | seeded, 4 + 3 switches | not seeded (names renamed away) |
| `stream_ref` / `stream_ref_xor_ic` (SALSA20, unused here) | not seeded | seeded, 8 + 8 switches |
| library switches | 134 | 145 |

The corrected file loses the ChaCha20 core's direct seeding and spends 16
switches on the Salsa20 reference implementation this workload never calls.
For this experiment the shipped file is the correct one and no seed change
applies. The general point is worth carrying forward: a name-keyed seed
format cannot address a static function whose name is reused across TUs,
and this rig's rename patch is the workaround. (The AEAD path was covered
either way, by propagation from the seeded public entry points; the
difference is direct seeding depth, not a hole.)

## The timing arms: two identical, one differs in one function

Rebuilt with the current compiler and byte-compared to the paper's binaries
(debug info and `.comment` stripped):

| arm | result |
|---|---|
| `gem5_base` | identical |
| `gem5_blanket` | identical |
| `gem5_taint` | differs in 1 of 1,276 functions: `crypto_onetimeauth_poly1305_donna_verify` |

In that function the instruction count (30) and the switch count (5) are
unchanged; one `msr DIT, #0`, the exit clear, moved from after the epilogue
restores (`ldp; ldr; add sp; msr; ret`) to before them (`msr; ldp; ldr; add
sp; ret`). Sub-block placement is not the cause: compiling the TU with
`-taint-dit-sub-block=0` and `=1` gives the same code. The only other
compiler changes between the paper's compiler (`9d698b0ddaa2`, an ancestor of
the tip) and now are the three commits of #21, so the move comes from the
refactor or one of its fixes; the likely mechanism is the epilogue block
flipping from On to Off (its only load, the callee-saved reload, is no longer
a Need), which puts the clear at the block entry instead of before the return.
That is a Phase 1 question, noted for the lead, not an experiment 02 one.

The function is the Poly1305 tag VERIFY, on the AEAD decrypt path. The
harness seals and never opens (no `decrypt`, `_open` or `verify` call in
`signed_lookup_gem5.c`), so the changed code never executes.

## Timing: the canonical lane reproduces to the cycle

All three arms, both switch models, six L values, five stack offsets: the
full canonical lane (210 runs, `gem5.fast` as the paper used, isolated
`WORK`) re-run with the rebuilt binaries. The runner's
`gem5_arms_off5.csv` is identical to `data/gem5_arms.csv` in 17 of 18 rows,
to the cycle. The `taint` arm, the one whose binary differs in a function
that never executes, matches at every one of its 12 cells:

| L | blanket | pass, renamed | pass, serialising | README |
|---|---|---|---|---|
| 10 | +7.3% | +0.2% | +41.2% | +7.3 / +0.2 / +41.2 |
| 50 | +12.7% | -0.9% | +32.1% | +12.6 / -0.9 / +32.0 |
| 200 | +20.2% | -1.0% | +17.7% | +20.2 / -1.0 / +17.7 |
| 1,000 | +27.8% | -0.3% | +5.1% | +27.7 / -0.3 / +5.1 |
| 5,000 | +30.5% | +0.2% | +1.4% | +30.6 / +0.2 / +1.4 |
| 20,000 | +31.4% | +0.4% | +0.7% | +31.3 / +0.4 / +0.6 |

(The 0.1-point differences are rounding: this table takes the median of
per-run IPC, the README's takes the ratio of the CSV's 3-decimal IPC
column; the underlying cycles are identical.)

The one row that moved is blanket at L=10: 4,281,549 cycles against the
paper's 4,281,080 (+0.011%), overhead 7.31% against 7.30%, spread 0.18%
against 0.15%. The binary is byte-identical, so this is the alignment
sensitivity the README already documents for the two secret-heavy blanket
cells (it reports that cell moving from +1.1% to +7.3% between path lengths);
the rebuilt runner's `/tmp` root hashes differently and one of the five
offsets landed a few hundred cycles away. It is 0.011% on a cell the README
already flags as alignment-sensitive to several points.

## Verdict, number by number

| README number | new | delta | cause |
|---|---|---|---|
| headline table, all 18 cells | same | 0 (one blanket cell +0.011%) | unchanged; the +0.011% is the documented alignment sensitivity |

| f_secret 66.54 / 22.54 / 1.56% | same | 0 | unchanged |
| "effectively sound; survivors are the checksum fold" | holds | - | unchanged |

Every claim survives as written. The one wording fix is the frontier's
"4 uncovered / 3,589 / 99.89%", which the run files (old and new) give as
"5 / 3,590 / 99.87%"; the sentence about the survivors being the checksum
fold is unaffected by one operation. Nothing in `data/` needs regenerating
for the paper: the compiler produces the same bytes on the two arms that
matter and the same cycles on all three, the oracle fix does not touch this
flow, and the seed file in use is the right one.

Not re-run: the pure-hash (q=0), q=0.5 and predictability-sensitivity
lanes. They use the same three binaries, two of which are byte-identical
and the third of which reproduced to the cycle across the canonical lane;
gem5 is deterministic, so they cannot move.
