Paper experiment 02 · libsodium

Signed-Lookup Crossover

Selective PSTATE.DIT placement beats blanket DIT below a secret fraction of 59%, by up to 21.7%. One request, two lanes — public table lookups and one ed25519 signature — with a single integer moving the ratio between them.

crossover measured, f* = 59% Apple M5 · kperf · 4 runs 4 arms · 5 knob points · 9 reps gem5: 4 arms, both switch models
The shape

Two lanes inside one call

The same experiment as the Bitcoin Core wallet, on a different workload. The knob direction is inverted: the secret lane is fixed at one signature and the public lane grows, so f_secret falls as L rises.

Public lane

lookup_lane(reqid, L)

L value-dependent loads into a hot 4 KB table. Each address depends on the previous load, so the chain is serial — the shape EVES and the data-memory prefetcher exist for. Never touches the key.

measured IPC0.75

Secret lane

crypto_sign(...)

One ed25519 signature over the gathered digest. Seeded through the project’s existing CIO-parity seed set rather than a seed file invented for this experiment.

measured IPC3.33

A 4.4× IPC gap between the lanes is what makes the knob work: moving L moves the mix between two microarchitecturally distinct regimes, not between two flavours of the same one.

The code

What the two lanes actually are

benchmarks/signed_lookup/signed_lookup_gem5.c

/* PUBLIC. Serial, value-dependent: the next address cannot be formed
   until the previous load returns. */
static uint64_t lookup_lane(uint64_t reqid, int L) {
    uint64_t acc = reqid * 0x9E3779B97F4A7C15ULL;
    for (int j = 0; j < L; j++) {
        acc += tbl[acc & tbl_mask];   /* value-dependent load address */
        acc = acc * 5 + 1;            /* keeps the chain serial */
    }
    return acc;
}

the measured region — identical under gem5 and on silicon

roi_begin();
for (int i = 0; i < iter; i++) {

    if (dosign) crypto_sign(sm, &smlen, (const unsigned char *)&d, 8, sk);
    sink += d + sm[0];
}
roi_end();

roi_begin and roi_end compile to gem5 pseudo-ops under -DGEM5_BUILD and to a monotonic clock plus kperf counters natively, so both instruments measure the same region of the same source.

A false start worth keeping

The first public lane had no prize

The first version hashed the accumulator to pick the index, over a 512 KB table. The reasoning was to avoid the lvp_chase trap, where a fixed traversal order is memorised by the value predictor after one pass and reports a 4.0× prize against 1–2% on real code.

That over-corrected. A hashed index into a large table is unpredictable by construction, and the result was a pure memory-latency benchmark:

first designIPCvalue predictionsblanket DIT costs
512 KB, hashed index0.2352,824 in 56M insts+0.01%
4 KB, hot table0.826—+11.92%

Real lookup tables are small and hot, and that is exactly what makes them predictable. Table size turned out to matter little across 4 KB, 32 KB and 512 KB once the index stopped being hashed — the prize lives in the serial dependence chain, not in cache behaviour.

Result

The crossover

Mean of two kperf runs with tail calls disabled, 9 rotated paired reps per point. Two earlier runs with tail calls enabled agree to within 0.4 points at every column. Negative pass − blanket means selective placement wins.

L is the knob — table lookups in the public lane per request. The secret lane is fixed at exactly one signature, so L alone sets the ratio: each request does L dependent lookups (~7 instructions each) and then one ed25519 signature that never changes size.

f_secret is a fraction of cycles, not instructions, measured per point by re-running with --nosign and taking (full − public) / full. That distinction matters here because the lanes sit at very different IPC — 0.75 against 3.3 — so the two fractions would not agree. Two workloads, opposite parameterizations, both finding a crossover.

The nop arm spans only −0.92% to +0.67% across every point, so none of this is the cost of restructuring the code — it is DIT. And at f=41% the pass runs faster than baseline, the same effect ed25519 shows: DIT gates optimizations that were net harmful on that code.

Where gem5 and silicon disagree, and it is not just magnitude

At high secret fraction silicon has the pass losing (+6.94% against blanket’s +0.78%); gem5 has it winning (+2.96% against +6.07%). The cause is visible in the table: gem5’s blanket costs +6.07% when 95.7% of the work is signing, so its model finds prediction opportunity inside ed25519 that the real M5 does not. On silicon, DIT over signing is roughly free.

Magnitudes are inflated about 3.3× throughout — blanket reaches +107.76% here against silicon’s +32.64% — which is the split this project sees everywhere: the simulator answers which structure, silicon answers how much.

The two tables also sit at different points on the f axis. gem5 reads f=17.3% at L=60,000 where silicon reads 4.0%, because the machines weight the lanes differently. Same knob, different f — so f* = 59% from silicon and “no crossover below 95.7%” from gem5 cannot be compared without matching on f first.

Mechanism

Blanket does not get slower. The baseline gets faster.

Blanket’s cost climbs from +0.78% to +32.64% as the secret fraction falls, which reads like DIT becoming more expensive. It is the opposite. Normalise to the cost of a single lookup:

Llookups measuredno DITblanketpenalty
50010,000,0001.957 ns1.960 ns+0.15%
2,00012,000,0002.019 ns2.040 ns+1.03%
5,00012,500,0002.001 ns2.056 ns+2.76%
20,00013,000,0001.845 ns2.065 ns+11.93%
60,00013,200,0001.582 ns2.066 ns+30.60%

Blanket is flat at ~2.06 ns per lookup at every L. The baseline falls from 1.96 to 1.58 ns. ~2.06 ns is what one iteration costs when it must execute serially — each address depends on the previous load, so the chain is pure latency. The only way to beat it is to break the dependence, which is what value prediction does: guess the loaded value, run ahead, verify later. DIT switches that off, so the serial latency is always paid.

The baseline improves with L because the predictor has to observe a pattern before exploiting it. At L=500 a request ends before much is learned, so DIT costs 0.15% — free. At L=60,000 the predictor is in steady state for tens of thousands of iterations and delivers a 19% speedup, all of which blanket surrenders.

A result that runs against intuition

More precise seeding made the pass slower

The first crossover used a secret lane covered by inherited DIT: one enable at the entry to signing and no switches inside it, because crypto_sign_ed25519 and SHA-512 were in translation units the seed set never named. Following the information-loss report to a fixpoint added five seed lines and gave the secret lane real placement — 64 to 82 switches in the binary, with SHA-512 going from 0 to 14 and the curve arithmetic from 0 to 4.

That made the pass worse where the secret dominates, and moved the crossover down:

The mechanism is the toggle-versus-coverage tradeoff appearing inside the secret lane rather than between the two lanes. Real placement in SHA-512 and the curve arithmetic means switches inside signing; where signing is 88% of the work those are pure added cost, and the pass’s bill more than doubles. f* moves 66% → 59%.

The one band it helps is the middle-low: −4.9 points at f=13%, where the pass now beats the unhardened baseline outright (−0.63%).

So a more faithful analysis is the more expensive one. That is worth stating plainly, because the instinct when a report says “taint stopped here” is that following it can only improve matters.

The measurement that nearly did not happen

The pass arm was blanket in disguise

The first pass arm entered the public lane with DIT already set on 100% of requests. It was byte-for-byte blanket, and every number it produced would have looked entirely plausible.

libsodium’s public crypto_sign is a two-instruction forwarder:

_crypto_sign:
  msr   DIT, #0x1
  b     _crypto_sign_ed25519      ; tail call - no epilogue, nothing ever clears

A tail call has no epilogue, so the mode is never restored and every instruction afterwards runs protected. The fix needed no compiler change: call crypto_sign_ed25519 directly. Same key, same algorithm, but it does real work after its own inner call, so it returns normally and placement can clear there.

The compiler now says this at build time rather than leaving it to be discovered:

taint: crypto_sign: DIT stays SET past this call: all later code runs
       protected, so selective placement degenerates to blanket coverage

And pub_dit — the fraction of requests entering the public lane with DIT set — is now a fatal gate in the runner, so this class of error aborts a sweep instead of producing a table.

The general fix costs nothing. Building the library with -fno-optimize-sibling-calls — a plain compiler flag, not the callee-saved ABI: no carrier, no frame slot, no mrs — removes every tail call, so placement has a real return to clear at. On libsodium that took the information-loss report from 7 severe leaks to 0, and the crossover moved by less than the run-to-run spread. Correctness for free. The ABI’s other half, which removes after-call re-asserts, is a separate and much more expensive proposition.

Instrument note

Absolute silicon IPC is measurable after all

Experiment 01 recorded that the M5 exposes no usable PMU, so every absolute IPC figure in the project came from gem5. That holds for /usr/lib/libkperf.dylib, which does not exist on this machine — but the private framework loads and exposes the kpc_* API:

/System/Library/PrivateFrameworks/kperf.framework/kperf   → 2 FIXED counters

On Apple silicon those two are core cycles and instructions retired — exactly IPC, with no event encodings to guess. Arming needs root (kpc_force_all_ctrs_set returns −1 otherwise), so the harness degrades to ipc=na and refuses to report rather than quietly falling back to timing.

Experiment 01’s ipc.md has been corrected accordingly. None of its numbers change — they are IPC ratios derived from timing under an equal-clock assumption, and the cross-instrument agreement below turns that assumption from bounded into confirmed.

The two instruments agree closely, which independently validates the equal-clock assumption experiment 01’s derived IPC figures rest on:

Method

Gates, in the order they run

Each one is fatal. The sequence is real: a workload that fails an early gate is not worth the next instrument.

  1. Blanket DIT costs something — natively, first Answered on silicon in seconds. If blanket is free the workload is a control, not a crossover, and no gem5 arms get built. Passed: up to +11.92%.
  2. Counters are armed Any run reporting ipc=na aborts the sweep instead of silently reporting timing as IPC.
  3. Each arm ran in the mode it claims The binary reads PSTATE.DIT back and prints it; a mismatch is fatal. sudo sanitises DYLD_*, so the blanket arm sets the bit in-process rather than by library injection — otherwise it would have become a second baseline.
  4. Retired instructions match between arms Blanket changes no instruction, so the counts must agree. Measured: ±0.01%.
  5. Arm order rotates every rep A fixed order lets frequency drift masquerade as an effect.
  6. Layout is separated from DIT The nop arm emits every switch as HINT #0 at the same address. Measured: −0.92% to +0.67% across all points, so restructuring is not the effect.
  7. Every arm actually narrows pub_dit must be 0 for every arm but blanket. It read 1.000 on the first pass arm, which was blanket in disguise. Now fatal.
Open

What is still missing

Matching the two instruments on f. The gem5 and silicon tables are indexed by the same knob but land on different secret fractions, so no crossover point can be compared between them yet. Sweeping L on gem5 until its f matches silicon’s would settle whether the disagreement at high f is a model artefact or a real property of the machines.

The public lane is synthetic. It is a dependence chain built to have the right shape, not a real application’s public code the way coin selection is in experiment 01. That makes the mechanism clean to read and the absolute numbers less transferable.

The secret lane is one layer deep. Seeding crypto_sign_ed25519 gave it real placement, and the report immediately named the next wall — crypto_hash_sha512 and the ge25519_* group. Going further would widen placement inside the signing; where to stop is a choice, not an oversight.
