The Secret-Fraction Crossover

Whether selective PSTATE.DIT placement beats turning DIT on for everything is decided by how much of the running time is secret — and the crossover is measurable inside a single unmodified call into shipped wallet code, by varying one integer.

A fixed prize against a growing toggle bill

Blanket DIT’s cost barely moves as the workload gets more secret — it protects everything either way. What moves is what selective placement pays: each additional signature is one more DIT region to switch in and out of. The crossover is those two lines meeting.

What is public and what is secret

Both lanes live inside one call to CreateTransaction, in the order the wallet runs them. Selection finishes entirely before any real key is touched, and the size estimate deliberately uses a dummy signer — so the secret work is one contiguous phase at the end.

# ---- SETUP (untimed) ----
wallet = CreateWallet()
repeat BTC_BENCH_CHAIN (5000): GenerateBlock(wallet)   # builds the UTXO pool
preset = pick BTC_BENCH_INPUTS coins

# ---- TIMED: one call into shipped wallet code ----
available = AvailableCoins(wallet)                  # enumerate UTXOs
result    = SelectCoins(available, target)          # 4 solvers; the prize is here
            → SelectCoinsBnB, CoinGrinder,
              KnapsackSolver, SelectCoinsSRD
size_est  = CalculateMaximumSignedTxSize(
              tx, DummySignatureCreator)            # dummy sigs, no key
txNew     = BuildAndSerialize(result, recipients)

if sign:                                            # BTC_BENCH_SIGN
  wallet.SignTransaction(txNew)                     # per input:
    CKey::Sign(hash, sig)
      secp256k1_ecdsa_sign(ctx, sig, hash32, seckey)
                                ^^^^^^ arg 3 pointee = the secret
Public — never reads the private key; amounts and UTXOs are on-chain data Secret — the only tainted work
The prize is one named mechanism. gem5 feature isolation attributes the entire public-lane cost to EVES, the value predictor: coin selection is a serial, value-dependent dependence chain, and DIT switches the predictor off. DMP, computation simplification and SIP contribute nothing measurable.

What blanket DIT costs in IPC

Absolute IPC is not measurable on this machine: macOS ships no usable PMU — no perf, kpc/kperf are private and root-only, and there is no xctrace without full Xcode. The change in IPC is exact anyway, and needs no counter.

Why the derivation holds. The two arms are the same binary, differing only by an inserted library that sets PSTATE.DIT process-wide. Blanket DIT changes no instruction, so with I fixed, IPC_blanket / IPC_base = t_base / t_blanket = 1/(1+C_whole). gem5 confirms the premise to the instruction on three separate runs: numInsts = 59,697,945, identical in both arms at both switch models. The duplicate-baseline arm bounds the one assumption, equal clock.

What this cannot settle

  1. Region count and secret fraction are confounded. Each signature adds both secret work and one DIT region, so this curve cannot separate “fraction decides” from “region count decides”. Disentangling it needs the chain-length knob, which moves the public lane at a fixed signature count. The rig supports it; it has not been run.
  2. The region boundary is not where the design note claims. Only C is instrumented in this build, so DIT regions sit inside libsecp256k1 per secp256k1_ecdsa_sign call — not at the C++ SignTransaction phase boundary. The measurement is valid; the prose needs fixing. A phase-level boundary would place one region per call instead of K, which is exactly the variable driving the crossover — so this is also the most promising follow-up.
  3. Closure is acceptable, not tight. Implied C_secret runs +4.52% against an independently measured +3.39%. Inside the gate, but the gap is unexplained.
  4. gem5 cannot confirm the magnitude here. It reproduces silicon’s always-on cost on the coin-selection kernel but reads essentially zero on ECDSA signing, where silicon is itself marginal. This is a silicon result; gem5 answers the switch-model question.
