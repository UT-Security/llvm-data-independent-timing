The Secret Leaves the Primitive

Experiments 09 and 02 both keep the secret inside one library call. This one lets it out: a TLS session ticket is decrypted by AES-GCM and then parsed by ordinary C that no shipping library annotates. Measured on the gem5 shadow-taint oracle: annotating every entry point of the crypto library still leaves the constant-time comparison that gates the handshake running unprotected, 547 operations on every resumption. The pass takes it to zero. It does not reach blanket coverage, and the page says where the rest goes.

The claim

Coverage. Annotating the primitive, which is what a developer writes first and what CryptoMPK's policy does by design, leaves every glue operation running with PSTATE.DIT clear. The gem5 shadow-taint oracle counts exactly how many. The pass covers them, because it follows the secret out of the primitive's output buffer.

Cost. It does so at the cost of the glue alone: not the cost of bracketing the whole resumption path, which is what a careful human writes with a scope guard, and not blanket's.

The experiment measures the gap between those three placements on a flow where the secret's lifetime is longer than the primitive's. The static gate has been run and is reported below; every other number on this page is a citation or an estimate the remaining gates exist to replace.

Where the secret goes

The server side of a resumed TLS 1.3 handshake in mbedTLS 3.6. Four functions in three translation units carry the resumption key after the decrypt returns. Function names from the 3.6 branch head.

Flow B, the literature anchor. The same rig in TLS 1.2 mode runs the RSA key exchange: mbedtls_rsa_private, then the constant-time PKCS#1 unpadding, then the version check and fake-premaster select in ssl_parse_encrypted_pms, then the PRF. That is the Bleichenbacher, ROBOT and Marvin glue in the library the attack chain named most recently (CVE-2024-23170). RSA key exchange is deprecated, which is why it is the second flow and not the headline.

Why this shape has backing

  • A 25-year attack lineage lives in the glue. Bleichenbacher 1998, ROBOT 2018, Marvin 2023, Kerberos PKINIT 2024. Marvin's own decomposition is the taxonomy: modexp, then padding check and secret extraction, then secret use and error handling. The leak keeps moving one call up.
  • Every C library ships that glue as straight-line constant-time C: OpenSSL rsa_pk1.c and tls_pad.c, mbedTLS constant_time.c, wolfSSL, NSS. Straight-line constant-time code is exactly what a value predictor still leaks from, and what PSTATE.DIT exists to protect.
  • The IETF concedes the boundary. RFC 8446 Appendix E.3: "even a constant-time padding removal function will likely feed the content into data-dependent functions."
  • Tickets are the deployed instance. About 40% of HTTPS connections at Cloudflare are resumptions; 77.6% of top-1M sites issue tickets; OpenSSL issues two per handshake. No library parses the ticket in constant time. There is no published attack on ticket parsing; flow B carries the literature, flow A the deployment.
  • No prior system measured it. ct-verif and Binsec/Rel verified one glue function without a cost. CryptoMPK declassifies every cipher output by policy, which erases this flow entirely.

What the analysis can and cannot see

Input flows are reported

A tainted argument reaching a callee in another translation unit keeps DIT on across the call, and -taint-info-loss-report names the seed that would narrow it. This is the loop 07 measured.

Output flows are not

When a callee takes public inputs and writes a secret through an out-pointer, which is what f_ticket_parse does for its caller, nothing tainted was passed, so nothing is reported. The consumer-side glue is invisible to prim and to the report. Only the oracle finds it. This is the 08 finding on a protocol flow.

Within one TU, or the whole library in pass-wl, a callee that writes a secret through a pointer makes the caller treat all memory as secret afterwards. Sound, and the origin of over-protection: after the ticket parse returns, the rest of its caller may run protected. The over-protection count is where pass-wl may lose to pass, and that is a precision result worth having either way.

Gate G0, measured

Run 2026-09-03 with the tree's clang on mbedTLS 3.6.2, aarch64 Linux, the design's configuration. Each variant of the whole library builds in 7 seconds. Precision inside the glue functions is 30 to 78 percent: the public metadata parsing next to the secret copy is swept in. That is the over-protection G2 will price against the bracket.

Blind spot 1: the mod-set gate

The RSA version check holds the premaster in a local buffer filled by a callee through an external call. The pass applies a callee's memory clobber only where a secret is passed in, and none is. With -taint-no-modset-gate the version check gets need = 83 and 6 switches, plus 7 more spread into the handshake step.

Blind spot 2: the function pointer

The ticket parse is indirect, so its caller sees nothing return, gate or no gate. The server's own copy of the resumption key into the negotiation state is an uncovered secret memcpy no report names. Found by reading the file; one seed line covers it.

Nine seed lines reach every named site; the annotation loop finds seven. Whole-library mode is dead: linking all 108 files and running the pass takes 17 seconds, but 83.3% of the library's instructions end up under DIT with the full seed set, with primitive-only seeds, and with five flow-A seeds alone. The spread is structural: once a caller's memory is TOP every argument is secret, every callee's clobber fires, and TOP is absorbing across the call graph.

Verdict. The probe passed its kill criteria: the glue is not a few dozen memcpy instructions, the pass reaches it, and the human's annotation misses all of it. It did not pass the hope that the pass finds the glue on its own. Next is one oracle run of the primitive-only arm on gem5 for the dynamic count.

Gate G1, measured: what a human annotation cannot reach

Run on the gem5 shadow-taint oracle over a real resumption rig: a TLS 1.3 client and server in one process, one full handshake to mint a ticket, then resumed handshakes as the measured region, with the server's ticket key as the seed. The first attempt used the deployed key exchange and the signal was buried under the ECDHE bignum it performs on every resumption. Pinning the client to pure-PSK resumption removes that and isolates the flow. Data in data/oracle_psk.csv.

mbedtls_ct_memcmp is the constant-time comparison that decides whether a resumption is accepted. It computes on the secret-derived binder. Operations of it running with PSTATE.DIT clear, per resumption:

That 547 is exact at one, two and four resumptions, a per-resumption invariant rather than an average. Naming every entry point of the crypto library does not protect the comparison that gates the handshake. It is not a crypto function and takes no key as an argument. The pass reaches it by following the secret out of the AEAD's output buffer, through the session loader and the PSK copy, into the compare. The human's scope guard is not zero either, because the client computes its own binder outside the bracketed scope: a guard protects exactly what it wraps.

But the pass is not sound here

Blanket leaves zero secret operations unprotected; the pass leaves 11,126 per resumption at its first seed round. This is a reduction in exposure, from 625,973, not an elimination. The next section measures what closing the rest would cost.

And the cost prize is small here

A pure-PSK resumption is almost all crypto, so blanket wastes 340,959 non-secret ops per resumption against the pass's 254,520, a factor of 1.34. That is experiment 09's lesson recurring: when the region is nearly all secret, no placement wins on cost. This experiment's contribution is soundness, not speed.

Why not just make it sound? The residual is a dial, not a wall

I pushed the pass as far toward soundness as its knobs allow: a second seed round naming the operation contexts, then the mod-set gate disabled for maximum conservatism. Both axes move together, every step.

Nothing reaches zero, and the closest configuration costs 93 percent of blanket. What survives is allocator internals reached from callers the analysis never considered tainted, the rig's transport stubs, and the generator state. So on this workload there is no setting that is both sound and meaningfully cheaper than blanket, which is the evaluation framework's first question answering "use blanket here" rather than a failure of the pass.

Which means the comparison that matters is not the pass against blanket. Where blanket is affordable it is strictly better: sound, and here only 1.34x the pass's over-protection. Selective placement earns its place only where blanket is unaffordable, at +32.6 percent on experiment 02's flow and +33.2 percent on experiment 03's small records, because a deployment that refuses to pay a third of its budget does not run blanket, it runs nothing. There, the pass competes with zero protection. This workload sits on the wrong side of that line and the page says so.

Soundness and cheapness are one dial. Blanket is trivially sound; the only way to cost less is to leave something unprotected; and the mechanism that buys coverage, keeping the bit set across calls the analysis cannot see into, is the mechanism that costs dwell. The libc share of the residual fell from 8,218 to 3,731 without instrumenting libc at all, because a protected caller leaves the bit set and the callee inherits it. Three things sit off the dial and no seeding removes them: the seed set is a human specification the analysis cannot derive, output flows across translation units are invisible to it, and declassification is unsound on purpose.

One caveat on the bulk figures. The oracle does not clear taint when a buffer is freed and reused, so the total residual of a hardened arm inflates with run length: the pass reads 11,126 uncovered ops per resumption over one resumption and 22,741 over four. The unhardened universe is stable at 1.07x, so the workload is consistent and the growth is the artifact. The figures above are the single-resumption run. The binder-compare count is immune to this, being exact at every run length.

Verdict, stated narrowly. Among selective placements, the only category that can cost less than blanket, the pass reaches glue that no annotation of the crypto library API reaches, and the binder compare is the named example: 547 unprotected operations per resumption under the strongest human annotation, zero under the pass. It does not achieve blanket coverage, and about a quarter of what it misses is addressable with more seeds rather than being a fundamental limit. On this particular workload, where blanket costs only 1.34x the pass in over-protection, an engineer who wants soundness should just set the bit.

Weaknesses, stated now

  • The glue is small. Hundreds of cycles of parsing beside microseconds of AEAD and HKDF. The cost result will be bounded; the experiment is about where protection lands.
  • No attack on ticket parsing exists. The page must not imply one.
  • The whole ticket plaintext is tainted by the seed, and the public fields are declassified by assertion.
  • Function pointers at f_ticket_parse, decrypt_func, f_rng, tls_prf. Seeds bridge them; the pass cannot hoist across them. Build with MBEDTLS_USE_PSA_CRYPTO so the ticket AEAD dispatches through PSA's switch tables rather than the cipher layer's function pointers.
  • The blunt mod-set may make pass-wl over-protect the rest of the handshake. If so, that is the result, and it names the next compiler change.
  • Inline assembly in bignum under MBEDTLS_HAVE_ASM sits inside flow B's primitive. Undefine it for the instrumented build and say so.
