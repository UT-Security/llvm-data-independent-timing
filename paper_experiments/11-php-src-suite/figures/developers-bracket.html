The Developer's Bracket

PHP's own benchmark suite, run three ways: with PSTATE.DIT set for the whole process, with the bracket a careful developer writes at the entry of each crypto function, and with the pass placing the switches. The suite is php-src's, the applications are the ones the PHP project benchmarks releases on, and the crypto is the applications' own.

The question

Setting DIT for a whole program costs whatever the program's public code loses when the predictors it relies on are switched off. Setting it only around the crypto costs the switches plus the barrier Apple's recipe puts after each enable. This experiment measures both on a benchmark nobody here wrote, and then measures whether an analysis that places the switches inside the crypto does better than the developer's bracket around it.

It feeds the paper's first and second questions: what DIT costs on shipping silicon, and what protection costs when it is placed selectively. Everything is measured on the M4, where MSR DIT serialises, so the numbers are the serialising column's silicon counterpart.

Where the secrets are

Three request types. Public work is the interpreter, the templates and the database round trip. Secret work is marked.

Anonymous page

The suite's default. Routing, queries, template rendering, HTML assembly. No secret is live at any point; this is the pipeline blanket pays for.

Logged-in page (WordPress)

The request carries two cookies. Before rendering, WordPress validates each one:

wp_validate_auth_cookie(cookie):
  parse  username | expiration | token | hmac
  user = lookup(username)                          # MySQL
  key  = hash_hmac('md5',    username|pass_frag|expiration|token, AUTH_KEY)
  mac  = hash_hmac('sha256', username|expiration|token, key)
  hash_equals(mac, cookie.hmac)
  hash('sha256', token) against the stored session token
then a handful of nonce checks for the admin bar, each an HMAC-MD5

A few thousand cycles of secret work inside a request of tens of millions. That is what deployment looks like, and it is the near-zero point of the sweep.

Login (both applications)

The password itself is the secret, and the work is chunky:

WordPress 6.2:  wp_check_password(password, stored)  → phpass: 8,192 rounds of md5(hash . password)
                wp_set_auth_cookie → the two HMACs above, to mint the cookies
Symfony Demo:   password_verify(password, stored)     → bcrypt, cost 13, ext/standard

All of it is PHP's own C: md5 and bcrypt in ext/standard, HMAC in ext/hash. No OpenSSL is on the path, which matters because OpenSSL's cipher dispatch would put a function-pointer call on every block.

The arms

Five binaries, one of them run in two modes. Every arm that adds instructions has a NOP twin with the same instruction count and addresses, so a comparison against the twin isolates what executing the switches costs from what moving the code costs.

The bracket goes on exactly the functions a developer would find by reading the applications: hash_hmac, hash, hash_equals, md5, crypt, password_hash, password_verify. The seeds for the pass name the same functions' key, password and data parameters. Both therefore treat every call of those builtins as secret-bearing, including the md5 calls WordPress makes on public strings. That over-approximation is stated as the policy, not hidden; it is what a developer with the same information would do.

The bracket on md5 is the interesting one. phpass calls the builtin 8,192 times per password check, so the bracket pays its enable, barrier and clear 8,192 times per login. The pass's region for the same work is decided by the analysis, not by the call boundary.

The knob

The share of requests that are logins, with the rest split between anonymous and logged-in pages. Five points: 0, 1 in 100, 1 in 20, 1 in 5, and logins only. The public work per request does not change with the knob; only how often the secret work runs. Symfony Demo takes the same knob with its own login.

Method

  • Per workload and knob point, the harness's counts: 50 warm-up requests, then 50 measured, each a php-cgi process, opcache on, JIT off, as the harness sets it.
  • Arms rotate every request so drift cannot masquerade as an effect. Wall and CPU time of each php-cgi process are both recorded; MySQL runs in its own process and is outside every arm equally.
  • Every process is started with the constructor dylib, which raises QoS for P-core residency and reads PSTATE.DIT back at exit. C must exit with the bit set, every other arm clear; a run that fails this is not a result.
  • Reported per cell: median, MAD, percent against A and against C, and the executed-switch term as P minus Z and B minus Bn.
  • No root, so no cycle counters: these are time percentages, which is what the questions ask.

The call-density sweep

The selective arms pay per crypto-builtin call, not per unit of time inside one, so the knob that moves them is calls per request. Two realistic settings raise it. REST requests authenticated by an application password make WordPress verify the password with phpass on every request, with no cookie to shortcut it. And a one-line plugin sets phpass to 216 rounds, a hardening setting sites use, which is 65,537 md5 calls per verification instead of 8,193. Same driver, 100 measured requests per arm after 50 warm-up, arms rotating.

The crossover. Blanket's fixed cost per request equals the bracket's per-call cost at roughly 10,000 to 19,000 crypto calls per request, and the pass's at 7,000 to 13,000. Every page request and a shipped-phpass login sit below it, where selective placement wins outright. A hardened phpass sits above it: at 216 rounds blanket costs 2.4 percent where the bracket costs 8 and the pass 11.7. The switch is the cost, and the application sets its count.

What it says

  • Blanket DIT costs a real PHP application 0.4 to 2.3 percent: about 2 percent on every WordPress request and under 1 on Symfony's. Zend/bench.php reads +10.8 on the same binary, so the micro-benchmark overstates the prize by five to twenty-five times, the same benchmark-versus-application gap the Django row showed for CPython.
  • The developer's bracket costs nothing on page requests, and 1.4 points on a WordPress login, where phpass calls md5 8,192 times and the bracket pays an enable, a barrier and a clear on each. At one login in twenty that is below the noise.
  • The pass matches the bracket on this suite: 1.6 points on the same login row, noise everywhere else. PHP's crypto builtins are leaves with no public work inside them, so the analysis has nothing to carve out that the bracket does not already exclude. Where the pass earned its keep earlier today was libsodium and the pilot's HMAC lane, whose regions the bracket cannot see; on a request pipeline whose crypto is a handful of builtin calls, the bracket is enough.
  • bcrypt is indifferent to DIT: 370 ms per Symfony login, +0.1 percent under blanket, zero switch cost for either selective arm.
  • Cost scales with crypto calls per request, and crosses blanket: 65,537 md5 calls per request (phpass at 216) cost the bracket 7 to 8 points and the pass 11.5, against blanket's 2. About 180 to 220 cycles per bracketed call, 300 per pass-placed pair of regions. Below roughly ten thousand crypto calls per request selective placement is cheaper; above it blanket is.
  • The pass costs more than the bracket where both are dominated by the boundary: it seeds PHP_MD5Update and PHP_MD5Final separately, so it enters two regions per md5 where the bracket enters one. Seeding the builtin's entry instead of the primitives would close that gap.
  • The deployment answer at a realistic login share, one in a hundred: blanket +2.3 percent on WordPress, bracket and pass within noise of unhardened. The prize is small, and both selective placements collect all of it.

What the outcomes were expected to mean, written before the run

  • C on the anonymous rows is the prize: the cost of DIT everywhere on a real request pipeline. The pilot says to expect something between the +11.7% of the interpreter benchmark and the +1.2% of the Django application, since a page request spends more of its time in the database driver and in memory traffic than the micro-benchmark does.
  • B on the login rows is the cost of doing what Apple suggests by hand: 8,192 bracketed md5 calls per WordPress login, each paying an enable, a barrier and a clear. If that is small, the bracket is enough for PHP and the analysis is a convenience. If it is not, the analysis has a job.
  • P against B, on the same rows, is the placement question with both arms paying the barrier. The pilot's HMAC lane says the pass adds about 2 points of switches over the dwell any protection pays; the bracket's cost depends on how many builtin calls a login makes.
  • P and B against C at 1 in 100 is the deployment number: at a realistic login rate, does either selective placement beat setting the bit for the whole server.

Limits, stated now

  • Both selective arms treat every crypto builtin call as secret-bearing, including hashing of public strings. Neither can see userland taint, and the paper should say so.
  • WordPress on MySQL is two processes; the arms differ only in php-cgi, and CPU time of php-cgi is the number that excludes the database. It is not a gem5 workload in this form; WordPress's SQLite integration plugin would make it one.
  • Instruction counts are the harness's metric and are not available here. Time on an idle machine with rotating arms and the DIT readback gate is the substitute, as in every silicon experiment in the tree.
  • Relinking PHP moved code layout by 3.9% in the pilot. Arms are compared against their own NOP twins, never against A alone.

What exists today

  • PHP 8.4.25 built with the taint compiler in three variants, ext/hash hardened, HMAC verified against the base build; ~/Documents/dit-silicon-candidates.
  • The compiler's -taint-dit-enable-barrier=sb flag, with the NOP control replacing the barrier alongside the switch; uncommitted with the default flip of the external-callee assumption and the test pins.
  • The timing harness with rotating arms and the readback gate, and the Zend pilot's four tables.
