# Benchmarks: what `bssl speed` runs, and which rows use DIT

Generated by `count_awslc.py` from the census of 2026-09-07 (`data/dit_census.json`); regenerate with `reproduce.sh census`. Every number below comes from that census, not from a reading of the source.

## The suite

AWS-LC v5.8.0's `bssl speed`, run with no filter and one thread, produces **632 rows in 304 families**. A family is a benchmark name; a row is that name at one input size (16, 256, 1350, 8192 and 16384 bytes for the byte-oriented ones, 2048 and 3072 bits for the prime-sized ones, a single row for the rest). The tool's `-filter` is a substring match on the row description and each filter runs as its own pass.

## Which rows enter the DIT bracket

AWS-LC's bracket is the `SET_DIT_AUTO_RESET` macro at the top of a public entry point: read PSTATE.DIT, set it, and restore it on return. To find which benchmarks pass through one, a fourth build (`ditcount`) counts the entries in `armv8_set_dit` and a patched speed tool reports the count over each row's timed loop. Entries per call is that count divided by the row's calls; it is an integer whenever the code path is deterministic.

| | rows | families |
|---|---|---|
| enter the bracket at least once per call | **381** | **213** |
| never enter it | 251 | 91 |
| whole suite | 632 | 304 |

Among the rows that enter, the median is 4 entries per call, the 75th percentile 5, the 90th 7, and the maximum 1,025 (CMAC at 16 KB: one bracketed single-block AES call per 16 bytes). The full per-family list is `data/dit_census.md`.

### Where the macro is in the source

`SET_DIT_AUTO_RESET` appears 181 times in 20 source files, by directory: fipsmodule/evp 71, fipsmodule/rsa 47, fipsmodule/dh 20, fipsmodule/cipher 13, fipsmodule/rand 5, fipsmodule/curve25519 5, evp_extra 5, fipsmodule/aes 4, fipsmodule/kdf 3, fipsmodule/ec 3, fipsmodule/hkdf 2, fipsmodule/tls 2, fipsmodule/sshkdf 1. It is absent from sha, hmac, digest, ecdsa, ecdh, ml_kem, ml_dsa, cmac, chacha and poly1305: those are bracketed only when a bracketed caller reaches them (EVP, the AEADs, the key-generation paths that draw randomness), which is what the census shows row by row.

## What the experiment runs

**Default run (`reproduce.sh`, `reproduce.sh 3`)**: the 25 filters in `data/bracketed_filters.txt`. The tool matches a filter against a per-benchmark selection name, not the row description ("AES-128" selects the block, EVP, AEAD and CMAC AES-128 rows; "ECDSA P-256" selects signing and verify together; "ECDSA P-256 signing" selects nothing), so the list is found by probing the tool with every prefix of every entering family and every literal its source compares the filter against, then choosing a set cover of the entering rows that costs the fewest row-runs (a row a filter selects runs under it whether or not another filter already covers it; a never-entering row costs extra). It selects **410 rows: all 381 that enter the bracket, plus 29 passengers that never do but share a selection name with rows that do (EC POINT P-224 add, EC POINT P-224 dbl, EC POINT P-256 add, EC POINT P-256 dbl, EC POINT P-384 add, EC POINT P-384 dbl, EC POINT P-521 add, EC POINT P-521 dbl, EC POINT secp256k1 add, EC POINT secp256k1 dbl, ECDSA P-224 verify, ECDSA P-256 verify, ECDSA P-384 verify, ECDSA P-521 verify, ECDSA secp256k1 verify, Ed25519 PKCS#8 v1 encode, Ed25519 PKCS#8 v2 encode, Ed25519 verify, HRSS decap, TrustToken-Exp1-Batch1 begin_redemption, TrustToken-Exp1-Batch1 redeem, TrustToken-Exp1-Batch10 begin_redemption, TrustToken-Exp1-Batch10 redeem, TrustToken-Exp2PMB-Batch1 begin_redemption, TrustToken-Exp2PMB-Batch1 redeem, TrustToken-Exp2PMB-Batch10 begin_redemption, TrustToken-Exp2PMB-Batch10 redeem, TrustToken-Exp2VOPRF-Batch10 begin_redemption, TrustToken-Exp2VOfPRF-Batch1 begin_redemption); they are run and kept, and the census marks them, so the analysis can set them aside**, with no row run twice. The driver reads the file as `BENCH_TESTS_FILE`; `BENCH_TESTS=...` overrides it. Run length: row-runs x 6 arms x 8 passes x the window, 410 row-runs here, about 2.2 h per run at 400 ms and 16 min at 50 ms.

**Paper stage (`reproduce.sh paper`)**: `BENCH_TESTS="AES-128,AEAD-ChaCha20-Poly1305,ECDSA P-256,RNG"` with `CHUNKS=16,1350,16384`: the ten rows of the paper table plus the other rows those selection names reach (the ECDSA P-256 verify row among them, which never enters the bracket and is not in the table).

**The recorded run in `results-m4/`** (before the census existed) used ten filters, `AEAD-AES-128-GCM,AEAD-ChaCha20-Poly1305,AES-128,SHA-256,HMAC-SHA256,ECDSA P-256,X25519,Ed25519,ML-KEM-768,RNG`, which select 127 rows in 51 families. 18 of those rows, in 6 families, never enter the bracket: `ECDSA P-256 verify`, `Ed25519 verify`, `HMAC-SHA256`, `HMAC-SHA256 init`, `HMAC-SHA256-OneShot`, `SHA-256`. They are kept in the recorded tables as what they are, rows on which the bracket costs nothing; the LaTeX band table leaves them out and says so in its caption.
