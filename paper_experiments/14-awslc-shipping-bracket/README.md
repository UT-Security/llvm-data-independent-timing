# 14 - AWS-LC: the bracket Amazon ships, on Amazon's own benchmark

**Status: complete, silicon.** Run twice on 2026-09-06 on the M4 (Mac16,10), CPU 9
hard-bound, PMC cycles per operation: once with 400 ms windows under a driver that still
discarded out-of-band samples (929 of 5,334, since recorded as such), once with 50 ms
windows and the no-drop driver (6,594 samples, 119 flagged, all kept). The two runs agree
to the cycle on every price below. `results-m4/` holds the second run (`data/` the build
record: diffs, switch counts, bracketed functions); the page is
https://claude.ai/code/artifact/a0c00df1-15d7-49bd-b8a2-79c940614a85 (source
`figures/shipping-bracket.html`, regenerated by `reproduce.sh analyze`). The design
sections that follow were written before the run and are unchanged.

**Rig:** `../../utils/dit_host_screening/awslc/`. **Run:** `./reproduce.sh` (section "How
to run"). The taint compiler is not involved: this experiment measures a library's own
bracket, built with the platform compiler the way its users build it.

---

## Why this workload

AWS-LC, Amazon's fork of BoringSSL and the crypto behind s2n-tls and the AWS SDKs, ships
the developer's bracket as a build option. With `-DENABLE_DATA_INDEPENDENT_TIMING=ON`
the macro `SET_DIT_AUTO_RESET` sits at the entry of the FIPS module's secret-handling
entry points (AEAD seal and open, EC scalar multiplication, RSA, the EVP sign, verify,
encrypt and decrypt paths, the DRBG, X25519 and Ed25519, HKDF and the TLS, SSH and
SP 800-108 KDFs, the single-block AES calls: 23 files) and does exactly this:

```c
#define SET_DIT_AUTO_RESET                      \
  volatile uint64_t _dit_restore_orig                \
         __attribute__((cleanup(armv8_restore_dit))) \
          OPENSSL_UNUSED = armv8_set_dit();

uint64_t armv8_set_dit(void) {          /* entry */
  ...  original_dit = armv8_get_dit();  /* mrs  s3_3_c4_c2_5            */
       __asm__ volatile(".inst 0xd503415f");   /* msr dit, #1          */
}
void armv8_restore_dit(volatile uint64_t *original_dit) {   /* every exit */
  if (*original_dit != 1 && ...) __asm__ volatile(".inst 0xd503405f");  /* msr dit, #0 */
}
```

Two facts about it matter here. It is the save/restore form (the same one experiment 12
had to use for nesting), with **no speculation barrier**. And the vendor's only
statement on its cost is qualitative, in `BUILDING.md`:

> With this build option, there is an effect on performance that varies by function and
> by processor architecture. The effect is mostly due to setting and resetting the DIT
> flag. If it remains set over many calls, the effect can be largely mitigated.

followed by their mitigation, hoisting the enable into the caller's scope (`bssl speed
-dit`), which "resulted in benchmarks that are close to the release build [...] when
tested on Apple M2". No number, no table, no per-function breakdown; the pull requests
(#1687, #1783) add none. So the shipped bracket has never been measured in public, and
the vendor's three claims (the cost varies by function, it is the switch itself, hoisting
recovers it) are all things this rig measures.

**What it is and is not.** It is experiment 09's shape: the benchmark is all crypto, no
public lane. Blanket should be near free and the bracket's cost should be its mode
writes per call, so it will show on 16-byte AEAD calls and per-block AES and vanish on
signatures. It cannot compare the bracket with the pass: the hot loops are assembly the
pass cannot reach, and `OPENSSL_NO_ASM` gives a build nobody ships. What it gives the
paper is the cost of the bracket a developer gets today from a FIPS library, on the
vendor's own benchmark, with the vendor's own claims checked, plus the price of the
barrier the vendor left out.

## The arms

Three builds of `bssl` from one source tree (AWS-LC v5.8.0), all carrying the same
speed-tool patch; two of them are also run in the vendor's hoisted mode:

| arm | build | run | executes per bracketed entry point |
|---|---|---|---|
| A | `rel`: DIT option OFF (the macro is empty) | | nothing |
| C | `rel` | `ENABLE_DIT=1`: the injected constructor sets DIT before `main` and nothing in the library ever touches it | nothing; a true blanket |
| B | `dit`: DIT option ON, as shipped | | `mrs` DIT, `msr dit,#1`; `msr dit,#0` at exit when it was off on entry |
| Bs | `ditsb`: B with `sb` after the enable | | Apple's recipe |
| H | `dit` | `-dit`: the vendor's mitigation, DIT set once around the whole run | `mrs` and `msr dit,#1` still execute at every entry; only the clear is skipped |
| Hs | `ditsb` | `-dit` | `mrs`, `msr dit,#1` and `sb` still execute at every entry; only the clear is skipped |

C against A is the dwell of DIT over the crypto with no switches at all. B against A is
the shipped bracket (and carries the layout difference of the DIT build, which has no
twin here). Bs against B is the barrier's price per operation. H against A is what the
vendor measured and called "close to the release build"; H against B is the per-call
clear and the DIT-off gaps it opens; Hs against H is the barrier's price in the hoisted
mode. A nested entry point (an AEAD seal calling into a bracketed cipher layer) runs the
entry sequence again, so one operation may carry several serialising writes: the counts
in `data/switch_counts.txt` are static sites; the executed count per operation is what
B - A divided by the per-write cost implies.

## Method

`tool/speed.cc` is patched (`patch_speed_pmc.py`) to read PMC0 (cycles) and PMC1
(retired instructions) with `isb`-ordered `mrs` around the same loop it already times
with `gettimeofday`, and to print both in each JSON row. Every row therefore yields
cycles per operation, instructions per operation and IPC at a read cost of about 39
cycles per timed loop of hundreds of milliseconds, with no kperf and no root. The counter
source is gated by `utils/cio_pmc_check.c` before anything runs.

**Single core, hard-pinned.** `bssl speed` runs its timed loop on one thread, and the
injected constructor binds that thread to one logical CPU through
`kern.sched_thread_bind_cpu`. Stock macOS has no affinity call (the Mach affinity policy
returns "not supported" on Apple silicon), but this M4 boots a development kernel with
`enable_skstb=1`, which exposes that sysctl; it is the same mechanism the SPEC and gapbs
studies' `cpupin.c` uses, and `utils/cio_ditctl.c` does it for every silicon rig when
`DITCTL_PIN_CPU` is set (the driver passes `PIN_CPU` through as that). The library's exit
line reports the core it bound (`pinned=9`) or `-1`. The write is a `kern.*` sysctl, so it
needs root: as an ordinary user it fails with "Operation not permitted" and the process
stays on QoS alone, which is what an unpinned run looks like. The run stage therefore
takes sudo for the driver alone and hands the results back to the user afterwards.

**Nothing is dropped.** Every sample enters the medians. Two things are checked and
reported next to the numbers, never used to discard: whether every process reported the
bind, `pinned=` equal to `PIN_CPU` (default 9; CPUs 0-5 are the E cluster on this part, 6-9
the P cluster), and each sample's implied clock, PMC cycles over the tool's microseconds. On a
pinned run only a clock no single P-core can produce, under 3.0 GHz (the E-core ceiling)
or over 4.7, means anything; a dip below the 4.4 GHz boost is DVFS under sustained load
and leaves cycles per operation untouched. The first pinned run on 2026-09-06 had a
4.0 GHz floor here and discarded 929 of 5,334 samples whose clock sat between 4.0 and
4.04 GHz while the kept ones sat at 4.04-4.46; those were valid, the gate was wrong, and
it is gone. Every sample's clock is saved in `speed.json`.

Per sample: one `bssl speed -json -timeout_ms 50 -chunks 16,256,1350,8192,16384
-filter <test>` process, one thread, hard-bound to CPU `PIN_CPU`, under the injected
constructor (DIT readback at exit: C must exit 1, every other arm 0; bind readback must
name `PIN_CPU`). Arms rotate on every rep; 1 warm-up rep
discarded, 7 kept. Tests: AEAD-AES-128-GCM (seal and open), AEAD-ChaCha20-Poly1305, AES-128 block
encrypt, SHA-256, HMAC-SHA256, ECDSA P-256, X25519, Ed25519, ML-KEM-768, RNG, each at the
five chunk sizes where sizes apply. Reported per row: A's cycles per op and IPC, every
other arm as percent over A, Bs - B and B - H in points of A, MAD of A.

## What the outcomes would mean, written before the run

- **C on every row** is the dwell: DIT over assembly crypto with zero switches. Experiment
  09 says to expect 0-2%; anything larger would be new.
- **B on the 16-byte AEAD rows and on AES-128 block** is the shipped bracket at its most
  expensive: two or more serialising writes on an operation of a few hundred cycles. At
  the M4's 26-41 cycles per write, one write pair should read as 15-30% on a 16-byte seal
  and as noise on a 16 KB one. If the per-op absolute cost (B - A in cycles) is constant
  across chunk sizes, the vendor's "mostly due to setting and resetting" is confirmed
  quantitatively; the constant also bounds the layout term, since layout cannot scale
  with the mode writes.
- **Bs against B** is the price of the barrier the vendor omitted, and **Hs against H**
  the same price when only the enable and barrier run per entry. Experiment 11 measured
  about 200 cycles for enable, `sb` and clear together on PHP's md5 path.
- **H against A** tests "close to the release build". H still pays one `mrs` and one
  serialising `msr dit,#1` per entry, so on 16-byte operations it should sit between A
  and B, not on A. If it reads as A, one write per call is free on this core; if it
  reads near B, hoisting the clear alone was never the fix and the caller must hoist the
  enable too, which is what the pass's twins do.
- **Signatures and KEM** should show every arm within noise of A: long operations,
  few crossings, DIT-insensitive arithmetic.

## How to run

```
paper_experiments/14-awslc-shipping-bracket/reproduce.sh          # pmc build run collect
```

Stages: `pmc` (gate: the kernel must expose the PMCs, otherwise every row's cycles would
be zero), `build` (downloads v5.8.0, patches, five `bssl` builds with the platform
compiler, `libditctl.dylib`, the gates; about 6 minutes), `run` (about 20 minutes on an
idle machine), `collect`. The gates count bracket *sites*, not mode-write functions:
AWS-LC compiles its FIPS module as one translation unit (`bcm.c` includes every file), so
with the option on the compiler inlines the bracket into each entry point, one `mrs DIT`
and two `msr DIT` per site, 277 sites in the shipped build; with it off only the two
out-of-line copies the speed tool's `-dit` path calls remain. `rel` must carry at most 2
`mrs DIT`, `dit` and `ditsb` at least 50, `dit` no `sb`, `ditsb` at least 50, and the PMC
patch must be in every binary. The build also writes the list of functions carrying a
site (`data/bracket_sites.txt` after `collect`).

Env: `W`, `PIN_CPU` (9), `REPS` (7), `WARM` (1), `TIMEOUT_MS` (50), `CHUNKS`, `HOST_TAG`, `BENCH_TESTS`,
`BENCH_ARMS`, `CC_BIN`/`CXX_BIN`, `JOBS`. Needs Homebrew `cmake`, `go` and `ninja`; Perl
is in macOS. Start it as your user: the run stage asks for sudo itself, uses it only for
the driver (the bind), and chowns the results back.

**The three prices**, from the two rows that enter exactly one bracketed function per
operation (the AEAD seal calls `EVP_AEAD_CTX_seal_scatter` directly; the single-block
AES call is its own entry point). Both runs, 400 ms and 50 ms windows:

| price | GCM seal 16 B | AES block |
|---|---|---|
| two mode-changing writes, B - A | 154 / 154 cycles | 94 / 94 |
| read + one non-changing write, H - A | 20 / 20 | -1 / -1 |
| `sb` after a changing write, Bs - B | 6 / 4 | 30 / 28 |
| `sb` after a non-changing write, Hs - H | 64 / 63 | 49 / 49 |

**Constant across sizes.** B - A on the GCM seal is 154, 153, 153, 162 and 175 cycles at
16 B, 256 B, 1350 B, 8 KB and 16 KB (max/min 1.14); GCM open 178 to 166; the EVP GCM
path 524 to 553. The cost is the writes and nothing else; it reads as 81% on a 16-byte
seal and 3% at 16 KB because the denominator moves.

**Nesting.** Dividing B - A by the price of one entry: the AEAD open path pays for 1.2
AEAD-level entries (its inner entry finds the bit already set and pays only the read),
the EVP cipher layer for 3.4 to 3.6, and CMAC at 16 KB for 1,029 single-block entries at
94 cycles each (one bracketed `AES_encrypt` per 16 bytes, plus the setup), which is +237%
at every size: the phpass shape, in a shipping library.

**The vendor's claim.** "Close to the release build" under hoisting is true above a
kilobyte and false below: H costs 10% on a 16-byte seal and 21% on a 16-byte open,
because every entry still executes a read and an enable; the enable no longer changes
the mode, so it costs 20 cycles rather than 154. Adding the barrier Apple's recipe
calls for puts the hoisted arm at 44% on the 16-byte seal (Hs), because a barrier
after a non-serialising write drains a full pipeline (63 cycles) where a barrier after
a serialising one finds it empty (4).

**Blanket.** Within noise on every crypto row, and faster than unhardened on the rows
that produce or consume fresh random bytes: RNG -25%, ECDSA signing -3.8%, ML-KEM
keygen and encaps -5%, Ed25519 key generation -8%. The hoisted arm H, which also holds
DIT on throughout, moves with C on every one of them. DIT disables the data-dependent
prefetcher on this core, and random words look like pointers to it: a hypothesis, not a
claim.

**IPC.** Cycles are instructions over IPC. The bracket adds about ten instructions per
entry; the cycles it adds come from the IPC it destroys: 4.14 to 2.34 on the 16-byte
seal, 1.94 to 0.74 on the single AES block, 2.47 to 0.85 on CMAC.

**Validity of the second run.** Bind reported by all 480 processes; 0 failures; 0 rows
without counters. 119 of 6,594 windows (1.8%) are flagged: their PMC delta is within a
few seconds' worth of cycles below 2^48, that is, the cycle counter read LOWER at the
end of the window than at the start, by 4 s to 3.5 h of cycles. They are spread evenly
across arms (18 to 21 each) and 78 rows, and are kept in the medians, which are robust
to one such value in seven. With a hard bind that pattern should be impossible; it is
recorded, not explained. `clock_probe.c` run pinned under sudo is the way to see it
directly. The other 6,475 windows sit at 3,879 to 4,461 MHz implied clock, median
4,172: the pinned core runs 4.0 to 4.2 GHz under sustained load, below its 4.4 boost.

## Limits

- One host and one library version. The bracket's placement is the vendor's, not ours;
  we do not add or move any `SET_DIT_AUTO_RESET`.
- `bssl speed` is a micro-benchmark: it measures the primitives, so it can bound the
  bracket's per-call price but says nothing about an application's public lane. That
  is experiments 11 and 12.
- No NOP twins: B and Bs are compared against A across a relink, so each carries the
  DIT build's layout term. The constancy of B - A in cycles across chunk sizes is the
  check on it; a layout term would not scale with the mode writes either, so the two are
  separable only by the switch-count argument, not by a control arm.
- The hard pin depends on a development kernel (`enable_skstb=1`) and on root. Otherwise
  the library reports `pinned=-1`, the process stays on QoS alone, and the driver reports
  the run as not pinned while keeping every sample; `PIN_CPU=` (empty) is the deliberate
  unpinned dry run, labelled as such.
- The PMCs are read inside the benchmark process, once per timed loop; the read cost is
  negligible against a loop of hundreds of milliseconds and identical across arms.
