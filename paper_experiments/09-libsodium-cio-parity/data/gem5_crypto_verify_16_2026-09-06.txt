================================================================================
2026-09-06. gem5 = worktree submodule at master ce05d32089; compiler 00f86ba06b5e.

blanket costs +8.39% on aes256gcm-decrypt and +0.41% on encrypt. blanket executes
no mode switches, so that is pure dwell -- the mode being on. This file is the
evidence for which DIT-gated optimisation the mode suppresses, and where.

comp-simp is INERT on both AES rows (compSimplifier.ditSuppressed = 0), which is
what the sweep's four gate notes report. The L1D prefetcher moves 2,127 -> 2,555
pfIssued with pfUseful 0 in both arms. So the whole +8.39% is EVES, the value
predictor, and on aes-decrypt the arithmetic is nearly 1:1 -- 4,590 predictions
lost, 4,513 cycles gained, 0.98 cycles per lost prediction.

It is NOT the volume of suppressed optimisation. ed25519 gives up 37,101
predictions AND all 21,992 comp-simp simplifications and pays 0.22%. What matters
is whether the predictions sat on the critical path.

3. WHY THOSE LOADS ARE PREDICTABLE
--------------------------------------------------------------------------------
libsodium's generic crypto_verify_n (src/libsodium/crypto_verify/verify.c):

    const volatile unsigned char *volatile x = (...) x_;
    const volatile unsigned char *volatile y = (...) y_;
    volatile uint16_t d = 0U;
    for (i = 0; i < n; i++) { d |= x[i] ^ y[i]; }

Both pointers are volatile AND volatile-qualified, and so is the accumulator, so
every iteration is forced through memory: three stack reloads per byte compared.
libsodium's constant-time idiom is what creates the value-predictable loads. The
volatile stops the COMPILER from breaking constant-timeness and in doing so hands
the MICROARCHITECTURE three perfectly stride-predictable reloads.

d is stride-predicted because on a successful verify it stays 0 every iteration,
so a stride-0 predictor is always right; on a FAILING verify it goes nonzero and
the prediction breaks. That is a value-dependent timing difference between "tag
matched" and "tag did not", i.e. the MAC-forgery channel this function exists to
close. Suppressing it is DIT doing its job.

PLACEMENT. The enable sinks past the whole five-instruction preamble to the first
Need; the clear hoists up past the last Need, ahead of the epilogue. Both boundary
instructions on each side are public and stay DIT-off. That is intra-block region
placement (-taint-dit-sub-block, default since 2026-09-05) behaving as documented.

NO HOLE IS CUT INSIDE, correctly: -taint-dit-sub-block-min-run is 8 and the longest
public run inside the covered region is 2 (add/cmp).

PRECISION. 25 instructions covered, 17 secret and 8 public -> 32% static
collateral. The loop runs 16 times, so dynamically 205 covered instructions per
call, 122 secret and 83 public -> 40% collateral. No finer placement improves it:
the public pointer reloads sit one instruction from the secret accumulator.

OF THE SUPPRESSED PREDICTIONS, 49 of 158 (31%) are on d -- genuinely secret, the
forgery channel. 109 of 158 (69%) are the two pointer reloads, which are public
addresses: collateral, buying no security, unavoidable at any granularity. The tag
BYTES (413038, 413040) are marked secret but were never value-predicted.

TWIN. crypto_verify_16.dit exists with identical taint classification and emits
ZERO msr DIT -- entered DIT-on by construction.

5. THE MEASURED COST IS THIS ONE FUNCTION
--------------------------------------------------------------------------------
aesni256gcm_decrypt/taint commits 100 DIT writes over 50 operations = 2 per op,
which is exactly this function's single enable and single clear. The entire
executed DIT cost of AES-GCM decrypt under ExpeDITe is the tag comparison.

And taint's renamed cost after subtracting its own layout twin (+8.20 points) is
essentially blanket's (+8.39), because it is paying the same dwell on the same
loop. That is the correct outcome, not a placement failure.

6. A RECORDED EXPLANATION THAT IS WRONG
--------------------------------------------------------------------------------
build_arms.sh's VARY_INPUT comment says CIO's drivers reuse one fixed 100-byte
message, which makes the kernel's loads predictable at their ceiling, "which is
the whole of blanket's cost on aes256-gcm decrypt". That arm was actually run:
data/gem5_api_bracket_vary_analysis.txt has blanket on aes-decrypt at +8.09%
against +8.39% here. Varying the message changes nothing. The cost is the tag
compare, which runs whatever the message is.
