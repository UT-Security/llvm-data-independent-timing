# Experiment 09 re-run, 2026-09-04

What happens to this experiment's numbers under the state of the tree on
2026-09-04: the compiler at the `dit-tainter` tip `7a4512b21fb7` (Phase 0
seed validation, the Phase 1 product-lattice domain, the Phase 2 flags all
off), gem5-DIT `master` `94d15692e5` carrying the store-rule oracle fix, and
the corrected libsodium seed file next to the shipped one. Everything was
rebuilt and re-run in isolated directories (`~/Documents/libsodium-cioparity-rerun`,
`~/Documents/libsodium-oracle-rerun-*`, `~/Documents/exp09-oracle-rerun`);
nothing under `data/` was touched. Silicon rows (M4, M5) cannot be re-run on
this host, which has no FEAT_DIT.

## Short version

- **The gem5 timing arms are byte-identical.** All 8 arm objects and all 54
  benchmark binaries rebuilt by today's compiler match the 2026-09-02
  originals to the byte once debug info and `.comment` are stripped, with the
  same switch counts (taint 524, taintfn 565, fine 639). The only MIR
  difference is two path-metadata lines. gem5 is deterministic, so every
  `gem5_*` number stands by construction; a control sweep is discussed below.
- **The oracle verdict is reproduced exactly, under both simulators and both
  seed files.** ed25519 sign: 294,164 protected, 0 clear; chacha20-poly1305
  AEAD: 7,170 protected, 0 clear; the null controls 294,164 and 7,170 clear.
  The store-rule fix, which cut mbedTLS's secret-operation count by 40%, moves
  nothing here, and that is itself a result (below).
- **One README number moves, and it is a diagnostic, not code**: the info-loss
  report grows from 23 records to 116 because the compiler now emits a
  `memory` category at severity UNSOUND. All 23 original records are present
  unchanged; the 93 new ones are the frame-address gap the argon2id
  correction already describes, now enumerated.
- **The seed file story is rig-specific and the earlier "12 dead lines"
  finding does not apply to the timing half.** Details below.

## The timing half

`build_arms_wl.sh mir arms link` with `LLVM=<build-subblock>`, the shipped
seed file, the same whole-library bitcode (`libsodium-wllvm-1.0.21`) and a
fresh CIO checkout for the drivers. Every object and binary compared
byte-for-byte against `libsodium-cioparity-repro/main` after
`llvm-objcopy --strip-debug --remove-section=.comment`: 8/8 objects, 54/54
binaries identical. This is the expected outcome given PR #21's own
byte-identity claim for libsodium, but it is measured here on this rig's
whole-library pipeline rather than the per-TU one, and it covers all nine
arms including the layout twins.

Two things the rebuild also shows. `uncovered.txt` and `callsites.txt` are
identical to their 09-02 originals (113 and 34 sites; the README's 126 is
from the other pipeline, below). `infoloss.txt` is not: 116 records against 23.
Every one of the original 23 (4 cross-TU, 19 indirect, all moderate) is
present; the 93 additions are all category `memory`, severity UNSOUND, with
the compiler's own wording "a frame address is passed to the callee while
this frame holds a secret, but the pointer register carries no pointee
taint, so NOTHING is transferred and the callee is analysed clean". Their
callers are the signing and verification paths (`_crypto_sign_ed25519_detached`
6, `crypto_sign_edwards25519sha512batch` 8, the HMAC verifiers) and the
callees are `sodium_memzero` (22), `crypto_hash_sha512_final` (7),
`ge25519_scalarmult_base` (6), `sc25519_reduce` (4); 4 of the 93 are argon2.
The README's "Is the secret actually protected" section quotes
`infoloss_records=23, infoloss_severe=0` from `static_policies.csv`; under
today's compiler that row reads 116 / 93. The oracle result below is what
says whether any of the 93 leaks at run time on the two audited workloads:
it does not. `ge25519_scalarmult_base` in particular runs entirely protected
because its callers hold DIT across the call, which is the inherited-coverage
mechanism the mbedTLS work found to be fragile but which holds on this seed
set.

## The oracle half

The oracle arms are a separate build: `benchmarks/crypto/build_libsodium.sh`
hardens per translation unit with `clang -ftaint-harden` from the vanilla
`libsodium-1.0.21` tree, and `benchmarks/taint_oracle/sodium_gem5.c` links
against it. The original libraries no longer exist on disk, so they were
rebuilt, six of them: `base`, `taint`, `taintfn` for each of the shipped and
corrected seed files. The rig's cross-compile wrapper requires a Mac-era
sysroot that is absent here; a native wrapper with the same include and
libm5 paths and no `--target`/`--sysroot` was used instead (the same way the
mbedTLS harness on this host is built).

Sixteen runs, 2 operations each as the README did: shipped seeds x {base,
taint, taintfn} x {sign, aead} under both the fixed gem5 and the preserved
pre-fix binary (`gem5.opt.storefix`), plus corrected seeds x {taint, taintfn}
x {sign, aead} under the fixed gem5.

Every number the README quotes is reproduced to the digit. Two observations
that are new:

**Why the store-rule fix moves nothing here.** On mbedTLS the fix cut the
per-resumption secret-operation count by 40.7%, because a secret-derived
allocation size (the leading-zero-limb trim) made the heap's top pointer
secret and every later pointer inherited it. libsodium's ed25519 and
chacha20-poly1305 keep every secret in fixed-size stack arrays and registers;
nothing secret ever sizes an allocation, so there is no pointer to
over-taint and the pre-fix and fixed oracles agree exactly. The
`secret-address` column is 0 in every arm, which is the same fact seen from
the other side. The paper's oracle numbers for this experiment never carried
the inflated denominator.

**The corrected seed file changes coverage, not the verdict.** With the 12
ChaCha20 lines corrected, the `taint` library gains 21 switches (129 to 150)
and the aead arm over-protects 60 more operations (2,106 to 2,166), because
`chacha20_encrypt_bytes` is now seeded directly instead of reached by
propagation. Protected and clear counts are identical: the secret was
already fully covered by inheritance.

## The seed file: two rigs, one file, two source trees

`data/seed_cio_parity.txt` and `benchmarks/crypto/libsodium_secret.txt` are
the same 65 lines. Twelve of them name post-rename-patch symbols
(`stream_ref_ref`, `stream_ref_xor_ic_ref`, `chacha20_encrypt_bytes_ref`),
because CIO's config was written against their patched tree.

- The **timing arms** are built from `libsodium-wllvm-1.0.21`, which carries
  the patch. There, all 65 lines are live and the shipped file is the right
  one. The "12 dead seeds" reported on 2026-09-03 were measured against the
  vanilla tarball and do not apply to this half.
- The **oracle arms** are built by `build_libsodium.sh` from the vanilla
  `libsodium-1.0.21`, which does not apply the patch. There, those 12 lines
  are dead, and the corrected file is the right one.

So the experiment's two halves have always used one seed file against two
different source trees, with 12 lines live in one and dead in the other. It
did not affect any published number: the oracle workloads take the IETF
path, whose functions are correctly named either way, and the shared
`chacha20_encrypt_bytes` was covered by inheritance. It should be written
down, because the next seed edit will hit it.

## The oracle-arm switch counts (134 / 137 vs 129 / 133)

The README notes the three oracle binaries carry 0, 134 and 137 `msr DIT`.
Rebuilt today they carry 0, 129 and 133. Rebuilding the same library with
the shared checkout's older clang gives 129 as well, so the gap predates
today's changes. The original oracle build was compiler `8d944025f4f6`
(2026-09-01); 18 commits since then touch the taint pipeline, and the
2026-09-02 commit that models `memcpy` instead of collapsing it to TOP is
the natural cause of a small drop in switches (fewer TOP clobbers, fewer
regions). Not confirmed by rebuilding that exact commit; the oracle verdict
is identical either way, so it is a footnote.

## The timing control: same bytes, three simulators

gem5 is deterministic, so with byte-identical binaries the only things that
can move a cycle count are the simulator and the guest's inputs. Two cells
of interest, chacha20-poly1305 encrypt and ed25519, arms base/taint(/blanket),
both switch models, were run under three simulators: gem5-DIT `master` with
the store-rule fix, `master` without it (`gem5.opt.storefix`, preserved), and
the very `gem5-DIT-pmull` binary (`ditcycles@2ca3920ec1`, built 2026-09-02
10:26) that produced the published sweep.

**All three agree to the last decimal**: cycles per op, instructions per op,
DIT writes, DIT cycles. The store-rule fix changes nothing in timing; the
oracle's bookkeeping is observation only, and this is the measurement that
says so.

**And they agree with the committed data.** `data/gem5_switch_model.csv`
matches today's cells exactly: ed25519 base 77,799.9, taint 76,716.9 (spec)
and 79,121.1 (serdit); chacha20-poly1305 encrypt base 2,212.1, taint 2,205.9
and 4,022.6. The quoted -0.28% / +81.85% and -1.39% / +1.70% fall out of
these to the digit.

One trap, for whoever reproduces next. `libsodium-cioparity-repro/main/out/
results.jsonl`, the work directory's own output file, does NOT match the
committed CSV: it reads 78,458.6 / 2,212.0 / 2,209.0 / 4,020.1, up to 0.84%
away and +4 instructions per op on ed25519. Its `config.ini` shows why: that
sweep ran the binary from a 71-character path under the work directory's
`canon/`, before the runner pinned argv[0] under a 31-character
`/tmp/cio_<hash>/` root. The README already names this exact mechanism
("a 0.84% shift from an argv[0] length change") and the committed CSV was
regenerated after the pinning; the stale `results.jsonl` simply survived
next to it. Compare against `data/`, not against the work directory.

Today's statics are exactly the gem5-arm flow's on 09-02 (524 / 565 / 639,
113, 34). So the experiment's committed numbers come from two compiler
states: the silicon arms and the static section from 09-01
(`8d944025f4f6`), the gem5 arms from 09-02, after the commits that model
`memcpy` instead of collapsing it to TOP and that report taint lost through
memory. Fewer TOP clobbers is what removes 14 secret-address sites and shifts
a few switches; the `memory` category is what adds the 93 UNSOUND records.
None of it changes a dynamic verdict: the oracle is 0 clear either way, and
the gem5 percentages are the 09-02 compiler's already.

## What survives, what moves

Survives as written: the claim (blanket -0.60% to +1.95%, selective placement
loses 12% to 124%); every gem5 switch-model number and both figures; the
oracle's 294,164 / 0 and 7,170 / 0 with their null controls; the CIO-parity
conclusion. The oracle numbers were never inflated on this workload.

Needs re-wording, none of it load-bearing: the static section's
`infoloss_records=23, infoloss_severe=0` reads 116 / 93 UNSOUND under the
current compiler (the 93 are the argon2id-style frame-address gap, now
enumerated; the oracle shows none of them leaking on the two audited
workloads); its 126 UNCOVERED reads 113; `static_policies.csv`'s 521 / 569 /
631 read 524 / 565 / 639; the consistency aside "0, 134 and 137 `msr DIT`"
reads 0, 129, 133. Each is the 09-01 compiler versus the 09-02 one, and the
README should say which compiler each table came from.

Two rig notes worth a sentence in the README: the oracle half and the timing
half build from different source trees (vanilla vs rename-patched) with one
seed file, so 12 lines are live in one and dead in the other; and the work
directory's `results.jsonl` predates the argv[0] pinning while the committed
CSV does not.
