# Experiment 09 re-run, 2026-09-06: Apple's bracket against ExpeDITe, both switch models

What Apple's own DIT idiom costs, what the pass costs, and how much of either is
switch serialisation rather than the mode being on. Seven arms, five benchmarks,
two switch models, 70 cells, every gate passed.

- compiler: `00f86ba06b5e`, all 2026-09-05 defaults (callee contract, DIT twins,
  intra-block region placement, external-preserves). Identical compiler sources
  to the current tip `2d995fec7045`, so the numbers are current there.
- gem5: **the worktree's own submodule** `gem5-DIT` at master `ce05d32089`, built
  from those sources
- data: `results/gem5/` - `results.{csv,jsonl}`, `analysis.txt`,
  `provenance.txt`, `crypto_verify_16.txt`, and a README covering the arms,
  the two switch models and the gates
- arms built in `~/Documents/libsodium-cioparity-exp09b`; nothing under `data/`
  from earlier runs was overwritten

argon2id is still running at the time of writing and will be appended.

## Short version

- **Under a renamed switch ExpeDITe's cost is at or below the noise floor on
  most rows** - but the floor is much wider than this run first assumed. Against
  the right denominator the renamed figures are -1.13, +1.16, +3.08, -6.26 and
  +7.43, against relink spreads of 5.40, 4.53, 7.04, 0.50 and 1.94 points. Three
  of five are inside their own spread and should be read as "indistinguishable
  from zero", not as a value.
- **Blanket is nearly free on four of five rows** (+0.22 to +1.31). The negative
  control still stands: with the workload all crypto, DIT-everywhere costs almost
  nothing, so selective placement is spending switches to recover close to zero.
- **Apple's bracket beats ExpeDITe on chacha and ties elsewhere.** The bracket is
  2 mode writes per call by construction; ExpeDITe emits 32 on chacha, so
  serialising costs it +38-39% against the bracket's +3-4%. On the other three
  rows ExpeDITe is *also* down to 2 switches per op and the two are comparable -
  `-taint-dit-external-preserves` and the twins doing what they claim.
- **aes256gcm-decrypt is the one row with a real dwell term, and it is one
  function.** blanket costs +8.39% there against +0.41% on encrypt. The cause is
  EVES value prediction inside `crypto_verify_16`, libsodium's constant-time tag
  comparison, which decrypt runs inside the timed region and encrypt does not.
  Full evidence in `results/gem5/crypto_verify_16.txt`.
- **The 2026-09-05 Apple-bracket table reproduces on a different gem5.** 61 of 70
  shared cells identical to the decimal; all 9 that moved are `spec` cells and
  the largest is 0.26%. Since the same binary runs under both switch models, a
  spec-only shift is a simulator-side change confined to the renamed path.
- **Two rig defects were found and one is fixed.** `lvp_pcs.py` attributed
  predictions over a window that is only ~51% ROI (fixed here). And
  `build_arms.sh`'s recorded explanation for the aes-decrypt row - the constant
  100-byte message - is contradicted by the `VARY_INPUT` arm that was run to test
  it.
- **A CSV reading hazard, not an error in the paper.**
  `data/gem5_api_bracket_apple.csv` carries two `api` row sets per cell: one with
  `dit_read = 0`, identical to `apibare` (the old two-write bracket), and one
  with `dit_read = 50` (Apple's real sequence). README's table reads them
  correctly as separate columns, but anything that takes the first matching row
  gets the wrong bracket - on aes-decrypt, +23.75% serialising instead of
  +26.87%. Filter on `dit_read > 0` for the Apple arm.

## The arms

| arm | what it is | mode writes / call |
|---|---|---|
| `base` | unhardened, the denominator | 0 |
| `blanket` | DIT set once before `main`, no analysis | 0 |
| `api` | Apple's sequence: `mrs` DIT token, `msr DIT,#1`, `isb sy`, call, conditional `msr DIT,#0` | 2 |
| `apiisb` | the same without the token read | 2 |
| `apiisbnop` | `apiisb` with `HINT #0` at the barrier's address | 2 |
| `taint` | `-ftaint-harden` at the shipped defaults | 2-32 |
| `taintnop` | `taint` with every switch a `HINT #0` | 0 |

`apidsb` (Apple's no-FEAT_SB fallback, `dsb nsh; isb sy`) was **dropped**: every
M-series has FEAT_SB, so it is a path no Apple device takes.

`apiisb` and `apiisbnop` earn their place on a simulator-specific ground. In gem5
`mrs DIT` decodes as `Mrs64, IsSerializeBefore`, a full pipeline drain, where an
M5 reads it in about 1 cycle. So `api` charges Apple's bracket for a cost that
exists only in simulation, and `apiisb` is what sizes that overcharge.
`apiisb - apiisbnop` is then the `isb` on its own.

`spec` = `--eves --dmp --comp-simp`; `serdit` = the same plus
`--no-speculative-dit`. Nothing else is passed. In particular no clear-shadow
flag: `--dit-clear-publish` stays at its default `frontier`, which is the policy
the submodule pin already ran (`983bbe2966`, "early publish of the DIT clear").
PR #108 named that policy and added `commit` / `writeback` / `rename` beside it;
it did not change the default path.

|---|---|---|---|---|---|---|
| aes256gcm-decrypt | +8.39 | +26.87 | +23.43 | +24.36 | +9.32 | 2 |
| aes256gcm-encrypt | +0.41 | +6.08 | +2.96 | +3.40 | -6.16 | 2 |
| chacha20poly1305-decrypt | +0.70 | +4.14 | +2.53 | +38.03 | +6.67 | 32 |
| chacha20poly1305-encrypt | +1.31 | +3.21 | +2.10 | +39.31 | +3.84 | 32 |

**Two corrections apply to the `taint` columns, and only to them.**

**The denominator was wrong.** `-taint-no-tail-calls` rides on `-ftaint-harden`,
so every pass arm pays a TU-wide tail-call disable that plain `-O2` does not: 44
tail calls become `bl`+`ret`, +0.89% library text, worth -0.91% to +3.49%
runtime depending on the row. `blanket` and `api` link the *unhardened* library
and keep their tail calls, so `base` is their correct denominator; the pass arms
belong on `rt` (`-ftaint-harden` with an empty seed file, zero switches). Against
`rt`:

| benchmark | `rt` vs `base` | `taint` serdit vs `rt` | `taint` spec vs `rt` | relink spread |
|---|---|---|---|---|
| aes256gcm-decrypt | +1.76 | **+22.22** | +7.43 | 1.94 |
| aes256gcm-encrypt | +0.11 | **+3.29** | -6.26 | 0.50 |
| chacha20poly1305-decrypt | +3.49 | **+33.39** | +3.08 | 7.04 |
| chacha20poly1305-encrypt | +2.65 | **+35.71** | +1.16 | 4.53 |
| ed25519 | -0.91 | **-0.59** | -1.13 | 5.40 |

**And the layout term it was previously corrected by is a lottery.** This run
originally subtracted each arm's NOP twin and reported a "switch term" of +0.16,
+0.57, -0.87 and +0.31 points. That subtraction is a single draw. `relink_null.sh`
links the *unhardened* library K bytes further along in `.text` - unreachable
padding, identical instruction stream, gate-verified identical committed
instruction count - and the same benchmarks move 0.50 to 7.04 points from that
alone. Six unreachable NOPs move chacha-decrypt +6.18%. Read as ensembles over 12
link offsets rather than one address pair, four of five arms' clouds overlap and
aes-encrypt's headline -6.33% layout term becomes **-0.15% median-to-median**.

So the "layout" column below is kept for the record, and is now known to be three
things - tail-call disable (mean 1.78 points), switch slots (1.41) and DIT twins
(3.53) - sitting on top of a draw the pass does not participate in:

| benchmark | layout (single draw) | renamed switch | serialising switch | total |
|---|---|---|---|---|
| aes256gcm-decrypt | +1.11 | +8.20 | +15.05 | +24.36 |
| aes256gcm-encrypt | -6.33 | +0.16 | +9.56 | +3.40 |
| chacha20poly1305-decrypt | +6.10 | +0.57 | +31.36 | +38.03 |
| chacha20poly1305-encrypt | +4.72 | -0.87 | +35.46 | +39.31 |
| ed25519 | -2.34 | +0.31 | +0.53 | -1.50 |

**What survives and what does not.** The serialising column survives easily:
+35.71 and +33.39 against `rt` on the chacha rows are thirty points clear of any
relink spread, and so is the gap to Apple's bracket at +3.21 and +4.14. The
renamed column does not: on ed25519, chacha-encrypt and chacha-decrypt the figure
is inside its own spread. Quote it as indistinguishable from zero, not as a
number.

**Per switch**, the only rows with enough switches to resolve it are the chacha
pair, at ~23 cycles serialising and ~0 renamed. Ignore the ed25519 figure the
analysis prints (332.9 cycles): that is 2 switches divided into a 78,790-cycle
operation, division noise rather than a measurement.

**The `isb`** (`apiisb` minus `apiisbnop`) costs 1-2 points on four rows and
+12.7 renamed on aes-decrypt. And on chacha, `api` measures *cheaper* than
`apiisb` (+2.53 against +5.90 spec) despite executing strictly more instructions.
Neither should be quoted as a barrier cost: both sit inside the relink spread
for their row (4.53 and 7.04 points on the chacha pair), which is the same
lottery the negative `taintnop` rows come from. `relink_null.sh` is how to put an
error bar on them.

## Why aes256gcm-decrypt has a dwell term

Full working in `results/gem5/crypto_verify_16.txt`. In brief:

`blanket` executes no switches, so its +8.39% is the mode being on and nothing
else. ROI counters say which optimisation: comp-simp is **inert** on both AES
rows (`compSimplifier.ditSuppressed` = 0, which is what the sweep's four gate
notes report) and the L1D prefetcher does not move. It is EVES, the value
predictor: 4,824 predictions -> 234, and 4,513 cycles gained, i.e. 0.98 cycles
per lost prediction.

An LVP trace names the code: **91% of the predictions inside decrypt's ROI are
three PCs in `crypto_verify_16`**, and inside encrypt's ROI that function
contributes zero, because encrypt has no tag to verify.

libsodium's constant-time idiom is what makes those loads predictable. Its
generic `crypto_verify_n` declares both pointers `volatile` *and*
volatile-qualified and the accumulator `volatile uint16_t`, so each iteration is
forced through memory - three stack reloads per byte compared. The `volatile`
stops the compiler from breaking constant-timeness and in doing so hands the
microarchitecture three perfectly stride-predictable reloads. The accumulator `d`
is stride-predicted because on a successful verify it stays 0; on a failing
verify it goes nonzero and the prediction breaks, which is a value-dependent
timing difference between "tag matched" and "tag did not" - the MAC-forgery
channel this function exists to close.

**The pass handles it correctly.** The enable sinks past the five-instruction
preamble to the first Need and the clear hoists up past the last, ahead of the
epilogue; no hole is cut inside because the longest public run is 2 against a
`min-run` of 8. Static precision is 17 secret of 25 covered (32% collateral),
dynamically 122 of 205 (40%). Of the suppressed predictions, 49 of 158 are on `d`
and are genuine protection; 109 of 158 are the two pointer reloads and are
collateral on public addresses - unavoidable at any granularity, since they sit
one instruction from the accumulator.

The measured cost *is* this function: `taint` commits 100 DIT writes over 50
operations, exactly its one enable and one clear, and the twin
`crypto_verify_16.dit` emits none. `taint`'s renamed cost after layout (+8.20)
being essentially blanket's (+8.39) is the pass paying the same dwell on the same
loop, which is the right answer rather than a placement failure.

## Reproduction against 2026-09-05, and what the switch model change is worth

Against the shared cells of `data/gem5_api_bracket_apple.csv` (reading its `api`
rows with a token read, `dit_read > 0`, which are Apple's real sequence):

**61 of 70 cells are identical to the decimal. All 9 that moved are `spec`
cells, none on `serdit`, and the largest move is +0.26%.**

| cell | 2026-09-05 | 2026-09-06 | delta |
|---|---|---|---|
| chacha-encrypt / `api` / spec | 2,225.9 | 2,231.7 | +0.26% |
| ed25519 / `taint` / spec | 77,386.1 | 77,193.4 | -0.25% |
| chacha-encrypt / `apiisb` / spec | 2,369.7 | 2,371.6 | +0.08% |
| chacha-encrypt / `apiisbnop` / spec | 2,344.9 | 2,346.8 | +0.08% |
| chacha-decrypt / `api` / spec | 2,347.0 | 2,347.8 | +0.03% |
| aes-decrypt / `apiisb` / spec | 1,315.0 | 1,315.3 | +0.02% |
| chacha-decrypt / `apiisbnop` / spec | 2,399.8 | 2,400.0 | +0.01% |
| ed25519 / `api` / spec | 79,177.1 | 79,167.9 | -0.01% |
| chacha-encrypt / `taint` / spec | 2,270.7 | 2,269.9 | -0.04% |

The spec-only pattern is the argument, not the magnitudes. **The same binary runs
under both switch models**, so a compiler difference would move `spec` and
`serdit` together. Only `spec` moved, which puts the change on the simulator side
and confined to the renamed path - the signature of the `frontier` clear-publish
policy, which has nothing to do under `serdit` because a serialising `msr` leaves
nothing in flight behind it. gem5's own design doc reaches the same verdict from
the other direction: the clear beats its commit by ~15 cycles on the crypto rigs
and `ditSuppressed` does not move, "the lead is real and mostly worthless".

So the earlier worry that master-tip gem5 would re-baseline the renamed column
was legitimate in kind - the commits do touch `rename.cc`, `iew.cc`, `commit.cc`
and the decoder - and is worth at most a quarter of a point in practice.

## Method notes

**gem5 came from the submodule, and the alternative was worse than a provenance
nit.** The rig scripts default `G5` to `~/Documents/gem5-DIT-pmull`, which is
`ba5083e237` - **51 commits behind the submodule pin**, and old in `rename.cc`
(+130 lines), `commit.hh`, `iew.cc` and `dyn_inst.hh`, including the commit that
introduced early publish of the DIT clear. Measuring on it would have modelled an
older `msr DIT` than the compiler at this revision is pinned against.
`~/Documents/gem5-DIT` is not at the pin either. This run built and used the
worktree's own `gem5-DIT/`. (Empirically the difference is small - see the
section above - but that is a result of the run, not something that was known
before it.)

Two things did *not* need redoing on that account: the 188-line contract seed
file is content-identical between `~/Documents/gem5-DIT` and the submodule (only
comments differ), and `libm5.a` is the stable m5op ABI.

**The rig scripts point at the submodule now, but that is not this run's doing.**
This sweep was set up by pointing `G5` at the submodule by hand, because at the
time `reproduce.sh` defaulted to `~/Documents/gem5-DIT-pmull` and the others to
`~/Documents/gem5-DIT`. `93ef1d242683` ("[rig] Every gem5 default is the in-tree
submodule, not ~/Documents") landed the same day and does it properly across the
whole tree, and `50e71be4caf0` bumps the pin to `ce05d3208955` - the same commit
this ran against. Nothing here needs redoing on that account.

`commit.ditCycles` and PMULL at `size=3` are also in master now, so the "TWO
PATCHES THAT ARE NOT UPSTREAM" block in `reproduce.sh` was stale; that is
corrected upstream too. The preflight still tests for the capabilities rather
than a branch name, so it still refuses a stock gem5.

**What this run does change is `lvp_pcs.py`** (the ROI window fix above), and
that is the only script edit it carries.

**Provenance against the tip.** The arms were built at `00f86ba06b5e` and this
document sits on `2d995fec7045`. Nothing under `llvm/lib`, `llvm/include`,
`clang/lib` or `clang/include` differs between them - the ten intervening
commits are tests, rigs, data and the pin - so the binaries and every number
here are current at the tip.

**The test suite.** At `00f86ba06b5e`, `taint-analysis-nonlocal-report.mir`
failed. That is a known stale fixture, not a regression from this work: it had
been failing since `fa4aa84e36a0` flipped the default to the callee contract,
and `dfa4725c4211` fixes it by giving `tailer` a secret operation of its own.
All 58 pass at the tip with the `lvp_pcs.py` change applied.

**`gem5.fast` reproduces `gem5.opt` exactly** - same cycles and same instruction
counts on both a hardened and an unhardened cell - so the argon2id stage runs on
`.fast`. Note `.fast` compiles out `--debug-flags`, so an LVP trace needs `.opt`.

**`lvp_pcs.py` is fixed here.** It took its window as the tick span from the first
measured stats dump to the last, but only ~51% of that span is inside the ROIs;
the rest is driver code between `m5_dump_reset_stats` and the next
`m5_reset_stats` - keygen, message setup, and the driver's *own*
`crypto_verify_16` correctness check. On encrypt the old code reported 212
`crypto_verify_16` predictions that were entirely the driver's, against 0 inside
the ROI - it would have said both benchmarks look alike, which is backwards. It
now filters per dump on `[finalTick - simTicks, finalTick]`.

**One recorded explanation is wrong.** `build_arms.sh`'s `VARY_INPUT` comment
says CIO's drivers reuse one fixed 100-byte message, making the kernel's loads
predictable at their ceiling, "which is the whole of blanket's cost on
aes256-gcm decrypt". That arm was run:
`data/gem5_api_bracket_vary_analysis.txt` has blanket on aes-decrypt at +8.09%
against +8.39% here. Varying the message changes nothing, because the cost is the
tag compare, which runs whatever the message is.
